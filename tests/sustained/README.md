# Sustained qualification

These are independently authored MIT test helpers, copyright 2026 Lee Bussy. They qualify the unchanged saved 0.0.1-rc.1 candidate under the [R1 policy](../../engineering/development/software-release-policy.md). R3 remains incomplete until both native architectures pass the full workloads and evidence validation. Diagnostic pilots never qualify. See the [R3 record](../../engineering/development/software-release-r3.md).

The owner selected `wspr5` for ARM64 and `ubuntu` for amd64. Each remote host runs a private Debian 12 filesystem in isolated mount, PID, network, IPC, and UTS namespaces. The privileged launcher prepares namespaces, then drops capabilities and runs the workload as UID 2001 with brewpi and www-data groups. It exposes generic PTY devices, read-only source and client inputs, and private writable lab/evidence directories. No Docker daemon, host account, systemd service, power setting, or radio configuration is changed. The Mac prepares and transfers inputs; target-side supervisors own the runs independently of SSH sessions.

[workloads.json](workloads.json) declares the fixed candidate identities, scenario, original profile schedule, durations, and budgets. A default full acceptance run performs eight constructed clock cases, eight persistence/alias fault cases, 100 lifecycle cycles, 24 continuous wall hours at 1x through the unmodified pinned host as sole serial consumer, and six continuous wall hours at 60x through an original sole client. The normal workload observes disabled/resumed profile segments; both sustained workloads require heating/cooling demands. Latency, incomplete-token timeout, ordered backpressure, repeated clock wraps, and input integrity are checked. A transparent relay observes the host stream without adding another reader. External host/panel code is separately staged, retains its own terms, and is audited unchanged.

[monitor.cpp](monitor.cpp) collects complete-child wait4 peak RSS. [sample.py](sample.py) independently samples identity, smaps_rollup RSS, descriptors, threads, CPU ticks, and monotonic/boot/UTC clocks every 0.5 seconds. Gaps over one second fail resource trends; heartbeat gaps over five seconds fail continuity. Both lifetime and sampled RSS peaks are gated independently; Linux accounting methods need not produce identical values. Full acceptance requires the fixed 128 MiB lifetime peak and 8 MiB steady-hour growth budgets. [validate.py](validate.py) reconciles saved raw resource reports, candidate receipts, and all workload results; [supervise.py](supervise.py) additionally verifies owned namespace cleanup. No interrupted run or shorter pilot is stitched into acceptance evidence.

Run `python3 tests/sustained/checks.py` for original negative regressions. Native Linux helper tests compile `monitor.cpp` separately and run `native_checks.py` as an unprivileged user. `stage.py stage HOST ARCH` prepares an explicitly selected target using the ignored, hashed root filesystem and candidate inputs under runs/r3/stage. `stage.py launch HOST ARCH` starts a diagnostic pilot; add `--acceptance` only after validated pilots and review of the fixed inputs. The explicit `--accelerated-only` option runs the outstanding six-hour workload plus clock/fault/lifecycle checks, retaining partial scope and `r3_complete=false`; it never claims the missing normal workload was executed. Use it with a separately reviewed complete normal-workload receipt, as documented in the [x86 recovery review](../../engineering/development/software-release-r3-x86-recovery.md). Launch receipts preserve target, runtime export, and harness hashes. Logs, failures, external captures, and package inputs remain ignored under runs/r3 and private target directories; collect them before removing any test directory.

The image recipe uses the existing pinned R4 build environment, Debian snapshot packages, and the existing hash-locked integration Python requirements. Exported filesystems are external tools, not MIT source artifacts. No emulator code is rebuilt or changed for sustained payload execution; only separate test helpers and the saved source's fixture driver are compiled. Physical Pi qualification, systemd activation, and the nine Arduino characterization cases remain separate.

The completed candidate qualification and retained evidence limits are recorded in the [final adversarial review](../../engineering/development/software-release-r3-final-review.md). Later main-branch controls changes are outside this saved candidate’s sustained evidence. Future runs retain individual n query timer values as well as summaries; earlier accepted runs retain reconstructed wire-trace distributions with their limitations documented.

For image preparation, use tests/integration as the Docker build context so its existing requirements.lock is available, and select the recorded R4 build image explicitly with the Dockerfile’s BASE_IMAGE argument. Preserve the exported filesystem hash and package inventories; a floating tag alone is not the identity of an accepted runtime. The exported images and prepared candidate/reference input tar files stay in the ignored staging area.
