# Repository instructions

Read [CONTRACT.md](CONTRACT.md), [CONTRIBUTING.md](CONTRIBUTING.md), and the [development guide](docs/development.md) before changes. Follow the [behavioral contract](engineering/protocol/behavioral-contract.md) and [firmware findings](engineering/protocol/firmware-findings.md). Arduino action/reaction is authoritative, including deterministic bugs. Undefined/artifact-dependent outcomes are disclosed limits, not invented replies or passing tests.

Author original implementation, tests, helpers, and documentation independently under MIT. Never copy, vendor, link, translate, adapt, or mechanically/AI-rewrite BrewPi/Fuscus implementation, headers, routines, generated tables, tests, or assets. Preserve contributor notices and source/helper SPDX identifiers. Required interoperability facts and standard equations are permitted. Use the [provenance gate](engineering/licenses/README.md#review-gate); external components retain their terms.

Keep source in `src/`, useful development tests in `tests/`, build/package utilities in `cmake/` and `release/`, scenarios in `config/`, optional service definitions in `systemd/`, current technical reference in `engineering/`, and user guidance in `docs/`. Document what exists and how to use it. Do not add dated progress narratives, plans, milestone/phase reports, or obsolete release discussions to the source tree or traveling package. Preserve required copyright/license text and native format identifiers.

Follow `.editorconfig` and `.clang-format`. Use one physical line per prose paragraph/list item, Oxford commas, and relative documentation links. Validate affected links, whitespace, build/package inputs, and meaningful tests. Keep normal validation isolated from physical controllers and working BrewPi state. Preserve unrelated work and public artifacts. Do not commit, push, tag, publish, deploy, activate services, change reference repositories, or access physical hardware without explicit owner authorization.
