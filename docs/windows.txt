Windows operation and source builds

The native Windows target is Windows 11 x64. The emulator opens one existing virtual COM endpoint; the serial client opens its paired endpoint. The emulator does not create ports or install drivers. Its controller, simulation, serial protocol, and local controls use the same independently authored MIT implementation as the POSIX executable. This does not provide a native Windows port of the BrewPi host or panel.

Prerequisites

Use an operator-provisioned virtual null-modem pair. The supported identity profile is HHD Free Virtual Serial Ports `7.35.01.1760`, with HHD virtual-device hardware ID `HHDVIRT\UniversalSerial4`, provider `HHD Software Ltd.`, and driver version `7.35.0.1753`. HHD is a separate proprietary prerequisite, excluded from the emulator archive. Its free edition prohibits commercial, government, and military use; obtain suitable external licensing before those uses. Do not disable Secure Boot, Memory Integrity, antivirus, or driver-signing policy to run the emulator.

The executable uses the external Microsoft Visual C++ v14 x64 runtime. Install it separately from Microsoft's official distribution when required. Python is unnecessary for headless or terminal operation. Readiness checks require Python `3.9` or later; the optional graphical LCD also requires a working `tkinter` extension and Tcl/Tk. Python, Tk, the COM provider, and runtime DLLs are not bundled.

Build and launch

Use Visual Studio 2026 with its x64 C++ tools and Windows SDK, CMake `4.2` or later for that generator, and Python `3.9` or later for development tests:

cmake -S . -B build-windows -G "Visual Studio 18 2026" -A x64
cmake --build build-windows --config Release
Push-Location build-windows
ctest -C Release --output-on-failure
Pop-Location

For a binary archive, extract it into a private directory. Extracted files inherit that directory's Windows permissions. The executable is `bin\brewpi-emulator-rmx.exe`, helpers are under `libexec\brewpi-emulator-rmx\`, and the standalone guide and notices are under `share\doc\brewpi-emulator-rmx\`. The Windows executable is unsigned. Compare `Get-FileHash -Algorithm SHA256` with the accompanying `SHA256SUMS` before extraction; checksums establish integrity, not publisher authentication. Windows or organizational policy can require per-application consent or prohibit unsigned execution. Follow that policy; the package does not weaken it.

Provide explicit `--serial`, `--serial-pair`, and writable `--state` arguments. COM names are canonical uppercase names such as `COM1` or `COM12`. Paths containing spaces or Unicode characters must be quoted. The application decodes its command line as Unicode and does not expand shell variables or `~` inside configuration values.

| Argument | Meaning |
| --- | --- |
| `--serial COMn` | Required selected emulator endpoint from the pair record. |
| `--serial-pair PATH` | Required operator-provisioned pair record. |
| `--state PATH` | Required writable local-drive controller store. |
| `--profile revc` or `--profile i2c` | Controller personality; default `revc`. See the profile pin map and saved-state rules (source archive: docs/operation.md). |
| `--scenario PATH` | Read-only physical scenario input, excluded when resuming. |
| `--speed FACTOR` | Simulated pacing from `0` through `1000`; default `1`, or the scenario/checkpoint value. |
| `--checkpoint PATH` | Save a checkpoint on eligible orderly shutdown. |
| `--resume PATH` | Restore a checkpoint with its matching controller store. |
| `--lcd MODE` | Local presentation; default `off`. |
| `--lcd-keep-on` | Disable presentation dimming. |
| `--help`, `--version` | Show usage or the application version. |

The pair record is an ordinary UTF-8 JSON file with these fields. Replace both COM names and instance IDs with those of the operator-provisioned pair; the other identity fields must match the supported profile:

{
  "format": "brewpi-emulator-serial-pair-v1",
  "provider": "hhd-vspt",
  "provider_version": "7.35.01.1760",
  "endpoints": [
    {"port": "COM1", "instance_id": "ROOT\\PORTS\\0000", "hardware_id": "HHDVIRT\\UniversalSerial4", "driver_provider": "HHD Software Ltd.", "driver_version": "7.35.0.1753"},
    {"port": "COM2", "instance_id": "ROOT\\PORTS\\0001", "hardware_id": "HHDVIRT\\UniversalSerial4", "driver_provider": "HHD Software Ltd.", "driver_version": "7.35.0.1753"}
  ]
}

The application checks both recorded devices against standard Windows device properties and opens only the selected verified virtual interface, exclusively. Missing, reassigned, physical, unsupported, and busy endpoints fail without scanning or falling back to another port. The peer relationship is operator-provisioned information: matching device identities do not prove that the provider currently wires those devices together. Replace and review the record after reprovisioning the pair.

For example, from the extracted directory:

.\bin\brewpi-emulator-rmx.exe --serial COM1 --serial-pair "C:\Users\example\pair.json" --state "C:\Users\example\AppData\Local\brewpi-emulator\controller.json" --lcd terminal

Configure the external serial client for the opposite endpoint:

port = COM2
altport = None

Use `57600` baud, eight data bits, no parity, and one stop bit. Client open/close and control-line changes do not trigger controller resets or serial replies. `R` remains an explicit controller restart. A client's input purge can intentionally discard queued startup bytes.

Readiness, controls, and shutdown

Use `--lcd off`, `--lcd terminal`, `--lcd gui`, or `--lcd auto`. Terminal controls require an attached Windows console with at least 23 columns and 15 rows. Type a command and press `Enter` to submit it; `press` is the rotary pushbutton action. GUI modes show the four-by-twenty LCD, physical heater/cooler/fan/light indicators, and an open/closed door icon. Counterclockwise and clockwise buttons flank the green encoder ring, with the press button in its center; full action names appear in tooltips. Indicators show physical load activation (`On`, `Off`, or `N/A` when no load is modeled), including custom wiring and polarity. Terminal presentation shows the same equipment and door states as text. GUI modes fall back to terminal presentation, then headless operation, when unavailable. See the control reference (source archive: docs/operation.md).

The readiness helper uses the state path, selected COM endpoint, and actual process PID:

python .\libexec\brewpi-emulator-rmx\wait-ready.py --serial COM1 --state "C:\Users\example\AppData\Local\brewpi-emulator\controller.json" --pid 1234 --timeout 10

It opens neither COM endpoint. The state path's `.ready` publication is private to the current account and names a private local message pipe. A fresh challenge verifies the live publication generation and endpoint; the PID alone is not authentication. A stale record after abrupt termination cannot answer the challenge. Ownership sidecars and the final inactive readiness record can remain beside state files; do not edit them while an instance owns them.

Stop client traffic, consume pending replies, and use `Ctrl+C`, `Ctrl+Break`, or the graphical window's close control for orderly shutdown. Closing a console window, ending the process in Task Manager, or abruptly terminating it does not guarantee a checkpoint. Use explicit writable paths with `--checkpoint` and `--resume`; checkpoint continuation requires the matching saved controller store and drained application output. OS-buffer acceptance does not prove peer consumption. Cross-OS checkpoint migration and universal power-loss durability are not claimed.

Troubleshooting

The supported HHD driver can leave a timed bulk read pending when fewer bytes arrive than the requested count, despite a finite total read timeout. External serial clients should read one byte at a time while assembling a bounded protocol line, or consume only bytes already reported as available. With pySerial, use `read(1)` with a finite `timeout` and an overall response deadline; do not use an arbitrary `read(4096)` to wait for a short reply. This provider limitation also occurs without the emulator; it does not require an LCD fallback.

If device checks fail, verify the provider profile, both instance IDs, COM names, and the actual pair wiring. Close other users of the selected endpoint. Do not substitute a physical port or disable security policy. State-file errors can indicate an existing owner, a read-only or busy file, a hard link, a reparse point, an ambiguous path, or a missing writable directory. Use an explicit local-drive state path outside the installed package. If GUI startup fails, check the external Python interpreter and its native Tk installation; headless and terminal operation do not require Python.

Local rotary and door controls

In an interactive terminal, type a command and press `Enter`:

| Command | Action |
| --- | --- |
| `cw` | Turn the knob clockwise. |
| `ccw` | Turn the knob counterclockwise. |
| `press` | Press the knob/pushbutton. |
| `door open` | Open the modeled physical door. |
| `door close` | Close it. |
| `help` | Display command help. |

`Enter` submits text; only `press` represents a pushbutton action. The GUI provides knob and door controls. Focus the knob and use `Left`/`Right` to turn and `Return`/`Space` to press; the door button is also keyboard accessible. Press opens the menu; turn to select an item, and press to enter or confirm it. Rotating through modes changes and saves the live mode immediately, including disabling targets when off is selected. A mode timeout restores the previous mode but does not restore disabled targets. Entering a beer/fridge temperature editor selects that constant mode immediately; rotation changes its displayed candidate, and confirmation quantizes and saves the target even without rotation. Temperature timeout leaves the previous target and the selected mode. Menu timeout uses ten firmware-clock seconds since the last logical change, with the source tick boundary; acceleration scales it, and at `--speed 0` it remains paused. Serial replies and ordinary sensor/control/output updates wait until the menu exits; the physical plant and firmware clock continue at the selected speed, and existing output levels remain latched. After UI initialization, logical encoder events received during another firmware wait are retained for the next eligible UI boundary. Events during startup display initialization are unavailable. Undefined invalid-mode lookup remains an explicit local fidelity limit rather than a normalized mode. Door input affects controller behavior only through the configured devices and modeled plant.

Text dims after more than sixty wall seconds without interaction. A deliberate turn or press wakes the screen and performs the action. `--lcd-keep-on` disables dimming. The terminal prompt stays readable. Local controls use private IPC and do not open another serial reader. Active menu state, retained logical encoder state, and queued serial bytes survive checkpoints. Presentation failure or close does not silently cancel the firmware menu or revert its live/saved changes. The emulator-only `cancel` action closes the menu without rolling back those changes. Physical encoder bounce, sub-grid blink phase, electrical UART errors, and electrical display timing remain outside this logical menu comparison.

During a modeled controller or TX wait, decoded serial input retains at most 63 bytes in arrival order; further arrivals are silently dropped, as in the retained Uno firmware. A long reply can fill TX, block command processing, and cause RX overflow. Wait for command replies before sending dependent work rather than flooding requests. Input delivered during startup display initialization is discarded before application RX is enabled. After startup or `R`, retry `n` until `N` arrives before sending dependent commands.

Incoming host bytes pass through a nominal virtual UART before the 63-byte RX queue; OS chunks are not treated as instantaneous bursts. TX models 63 software bytes plus the two peripheral positions and nominal 170-microsecond frames. Full TX suspends the current action while clocks/plant time continue and outputs remain latched; serial work resumes before the next ordinary controller evaluation. Positive pacing scales UART time with controller time. At zero speed, RX/TX continue at 1x while runtime controller/plant clocks stay paused. Large host writes can overflow RX if their serialized arrivals outpace a blocked consumer. This is a decoded-byte model, not physical wire timestamps, oscillator/ISR timing, parity/overrun errors, or USB buffering; see the UART evidence and limits (source archive: engineering/protocol/firmware-findings.md).
Scenarios and simulation time

The source tree provides `config/active-fermentation.json` for fermentation heat and `config/room-cycle.json` for a daily room cycle. Binary users can create a JSON scenario using the configuration guide and pass its path with `--scenario`. See scenario fields (Scenario configuration below) for the supported physical parameters. Scenario files are read without modification.

`--speed 1` uses real-time pacing. Factors such as 10 or 60 accelerate simulated physics and controller time without changing controller thresholds or the integration step. Zero pauses scheduled simulation while synchronous commands and wall-clock token deadlines continue. Host fermentation profiles, CSV dates, and chart timestamps remain wall-clock based; acceleration does not accelerate the host's profile schedule.

The serial parser follows firmware framing and partial-input behavior rather than a general strict JSON API. Incomplete tokens can wait about one wall second. A slow reader defers input/controller work while replies remain queued in order. Drain existing output before expecting another command's response.

Both personalities' hourly display initialization briefly defers serial commands while simulated time continues. A checkpoint taken during this pause retains its pending input; resuming it at `--speed 0` holds dispatch until simulated time advances. Use positive pacing to finish that pause. See the qualified behavior and timing limits (source archive: engineering/protocol/firmware-findings.md).

Startup and serial `R` include the selected display's mandatory initialization waits before normal dispatch. Configured probe reset states can add conditional conversion waits; already initialized probes and DATA-only recovery do not acquire a universal 750 ms delay. Startup advances controller and plant time at the selected positive speed; with `--speed 0`, startup completes at 1x before the runtime clock pauses. Resuming a checkpoint already in ordinary sensor or hourly-display blocking retains the pause until positive pacing resumes. See probe reset scenarios (Scenario configuration below).

Scenario configuration

Pass a JSON file with `--scenario PATH`. The emulator rejects unknown fields, invalid physical parameters, and input/output path aliases. Omitted fields use the built-in defaults. Inputs are read without modification. A scenario sets external equipment/initial conditions; it does not change firmware constants or replace a resumed checkpoint history.

Select the controller personality separately with `--profile revc|i2c`; the default is `revc`. When `physical_loads` is omitted, default heater/cooler/light/fan pins are 5/6/2/19 for RevC and 6/5/2/10 for I2C. An explicit load list is used exactly as written in either profile. `instance_id` continues to select the supported synthetic probe identities, not the controller profile. See the profile and saved-state rules (source archive: docs/operation.md).

The source tree includes active-fermentation.json (source archive: config/active-fermentation.json) and room-cycle.json (source archive: config/room-cycle.json). For a standalone binary, create a scenario file, for example:

{
  "initial_temperatures_c": {"beer": 20, "chamber": 20, "room": 22},
  "fermentation_enabled": true,
  "random_seed": 1
}

Fields

| Field | Meaning and units |
| --- | --- |
| `initial_temperatures_c` | Object with `beer`, `chamber`, and `room` initial temperatures in degrees Celsius. |
| `beer_liters` | Beer volume in liters; default five US gallons, approximately 18.927 liters. |
| `beer_density_kg_per_m3`, `beer_specific_heat_j_per_kg_k` | Beer density and specific heat. |
| `carboy_capacity_j_per_k` | Carboy heat capacity. |
| `chamber_liters`, `air_capacity_j_per_m3_k`, `cabinet_capacity_j_per_k` | Chamber air volume, volumetric heat capacity, and cabinet heat capacity. |
| `beer_chamber_conductance_w_per_k`, `chamber_room_conductance_w_per_k` | Thermal coupling between beer/chamber and chamber/room. |
| `physical_loads` | Array of objects with `pin`, `kind` (`heater`/`cooler`/`light`/`fan`), nonnegative `watts`, and `active_low`. The `cooler` kind removes heat; other kinds add it. Pin assignments must be unique. |
| `probe_reset` | Three booleans in physical beer/chamber/room probe order, independent of assigned functions; default all false represents probes with readable completed values. A true entry represents a probe reset indication that requires connection setup and the conditional 750 ms conversion wait when firmware initializes that probe. This is independent of a DATA-only disconnect. |
| `probe_quantization_c`, `probe_lag_seconds`, `noise_amplitude_c` | Probe quantization, lag, and noise magnitude. |
| `random_seed` | Deterministic pseudo-random seed. |
| `room_daily_amplitude_c`, `room_daily_phase_hours` | Daily room-temperature sinusoid amplitude and phase. |
| `door_pin`, `door_open`, `door_extra_conductance_w_per_k` | Modeled door input and added heat transfer when open. |
| `fermentation_enabled`, `fermentation_age_hours` | Enable fermentation heat and set its initial age. |
| `active_fermentation_profile` | Object with `maximum_watts` and `breakpoints_hours_watts`, an ordered array of `[hours, watts]` pairs. At least two points are required, hours must increase, and the final power must be zero. |
| `instance_id` | Hardware identity profile; `chamber1` is the supported value. |
| `speed_factor` | Initial simulation pacing factor; `--speed` overrides it. |

Use separate files/directories for scenarios, controller stores, checkpoints, PTY links, and locks. Repeatability requires the same configuration, seed, and input/event history. Host profiles and chart timestamps remain wall-clock based.

Examples and scenario documentation are original MIT work. See model details (source archive: engineering/protocol/controller.md) for arithmetic, defaults, and checkpoint behavior.
