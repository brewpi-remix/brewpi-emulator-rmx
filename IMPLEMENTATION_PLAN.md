# BrewPi emulator implementation plan

Status: milestone 1 specification/data deliverable completed for owner review on November 13, 2026. Emulator implementation has not started and remains unapproved. The public repository is [brewpi-remix/brewpi-emulator-rmx](https://github.com/brewpi-remix/brewpi-emulator-rmx); local main tracks origin/main. The initial scaffolding commit was published earlier; the owner subsequently authorized committing and pushing the reviewed milestone 1 artifacts and supporting documentation to main.

## Governing decisions

Create an independent native C++ Linux application that replaces an Arduino for hardware-free BrewPi Remix integration testing. The owner's latest instruction resolves every ambiguity in favor of the Arduino firmware's actual action/reaction, including bugs. Document defects; do not fix their behavior by default. This supersedes earlier proposed atomic validation, stricter device checks, corrected filter/control behavior, extra telemetry, nominal-only defaults, and new LCD/annotation wording. The current [behavioral contract](engineering/protocol/behavioral-contract.md), [defaults](engineering/protocol/defaults.md), [diagnostics](engineering/protocol/diagnostics.md), and [findings register](engineering/protocol/firmware-findings.md) are normative for milestone 1 topics.

Original code, helpers, tests, configuration examples, fixtures, and prose use [MIT](LICENSE.md), with contributor notices retained and source SPDX identifiers where appropriate. Required interoperability names/values and wire phrases are specification facts, not permission to copy implementation. Do not copy, vendor, link, translate, mechanically rewrite, or adapt firmware/Fuscus code, source declarations, macros, routines, tests, generated tables, or assets. This remains source-informed independent development, not a formally separated clean-room claim. The [project contract](CONTRACT.md) and [licensing review gate](engineering/licenses/README.md#review-gate) govern provenance. Existing host/panel processes are permitted external compatibility clients.

The initial system is one chamber with a carboy containing five US gallons of beer, three separate physical temperatures, fermentation heat, fixed virtual probes/loads, persistent firmware-like configuration, repeatable external scenarios, and optional clock acceleration. USB descriptors, actual GPIO, firmware flashing, glycol, DS2413 hardware, and additional external panels are not initial hardware scope. Firmware command behavior still follows the selected build, including accepting some stored records whose functions have no live target; absence of modeled hardware is not permission to invent validation errors.

## Source-backed conclusions

The real host accepts an explicit PTY path; USB auto-discovery and installer USB-serial pairing do not apply to a PTY. Use a configurable stable path, default /run/brewpi-emulator/chamber1/serial, altport=None, and optionally startupDelay=0. A host process may need reopening/restart when an emulator process replaces its PTY. No host/panel code change is currently required for the normal workflow. Sources: [serial setup](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/BrewPiUtil.py#L376), [USB discovery](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/autoSerial.py#L38), and [installer pairing](https://github.com/brewpi-remix/brewpi-tools-rmx/blob/7e95e19796bed3e8cd6aa08f08f89db05ac66fa4/install.sh#L458).

The ordinary firmware protocol is not a new strict JSON API: token parsing, incremental writes, field types, partial failures, timing, annotations, LCD bytes, and diagnostic ordering must be preserved. Device schema/host cache and panel workflows are traced in the contract. Some apparent bugs, including unchecked duplicate assignments and incorrect live beer-filter routing, are required deterministic behavior. Memory-undefined or hardware-dependent actions have explicit characterization cases without invented exact responses. Sources: [serial/controller interface](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp), [device implementation evidence](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp), and [actual host workflow](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1097).

The existing firmware simulator was evaluated: it models beer/chamber heat capacity, conduction, room variation, actuator watts, and fermentation heat, but its build suppresses OneWire discovery, changes telemetry/settings responses, and auto-installs probes. Its thermal defaults/bugs are documented reference observations, not code to reuse. The emulator's independent external plant represents physical brewing hardware while the ordinary controller personality stays faithful. Historical Fuscus demonstrates PTY use but leaves device/update/reset paths incomplete and uses real Pi hardware; it is not a source dependency or compatibility oracle. Sources: [simulator](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Simulator.h), [simulator loop](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Simulator.cpp), [forced simulator sensors](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/SettingsManager.cpp#L52), and [Fuscus protocol gaps](https://github.com/brewpi-remix/fuscus/blob/ac371054ed181afff1c1b74f9be8e93d5a86c8e1/fuscus/piLink.py#L179).

## Architecture and dependencies

| Module | Responsibility |
| --- | --- |
| Serial transport | Linux PTY, stable link ownership, reconnect behavior, byte buffering, and wall-clock firmware-style token waits. |
| Protocol adapter | Original handling of the reference command grammar, response types, nested diagnostic placement, and exact required wire semantics. |
| Device registry | Synthetic external inventory plus firmware-like saved slots/live targets, including documented validation and discovery quirks. |
| Controller | Independently authored matching mode/filter/PID/state/timer action/reaction; do not insert behavioral fixes. |
| Thermal plant | Independent physical beer/chamber/room model, fermentation heat, probe locations, electrical pin loads, and optional disturbances. |
| Simulation clock | External plant time, reference-width controller clock, pause/acceleration, and deterministic scheduling. |
| Persistence/scenarios | Firmware-like EEPROM validity/write side effects, separate stable physical identities, repeatable external initial conditions, and coherent optional checkpoints. |

Use original C++17 code with the standard library and POSIX/Linux APIs; no incorporated third-party JSON/controller library is selected. This resolves the earlier JSON-library proposal. CMake/system compilers are external tools; actual compiler/tool versions and Python/pyserial test environments will be recorded when selected/exercised. No dependency was installed, fetched, vendored, or executed for milestone 1. Linux x86_64 and ARM64 are initial software targets; the owner's exact Pi OS/model is a qualification input. All incorporated material must satisfy the independent MIT/provenance gate; reference source retains its own license.

The external thermal balance tracks beer and chamber energy against a separate room boundary, with fermentation input, heater/cooler power, auxiliary heat, and conductance. The exact original scenario values, capacities, physical pin map, probe quantization, fermentation curve, and initial seed are frozen in defaults. Model elapsed physics rather than canned temperature traces. The fixed controller behavior is judged against its own sensor input history; thermal plausibility does not excuse protocol or control divergence.

Acceleration changes how quickly simulated seconds advance, not firmware timer thresholds or integration step size. Host fermentation profiles, serial deadlines, CSV dates, and chart timestamps remain wall-clock based. Default panel checks use 1x; accelerated constant-target/scenario tests must not claim accelerated host-profile equivalence. R reboots the controller while external plant state persists; ordinary process restart loads firmware-saved settings with the configured fresh external plant; explicit checkpoint resume restores coherent controller/plant/history state without adding downtime. Sources: [host profile clock](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/temperatureProfile.py#L45) and [chart dates](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpiJson.py#L64).

## Milestones and acceptance

1. **✅ Behavioral contract and original fixtures, complete for review.** The [milestone review](engineering/development/milestone-1-review.md) maps every gate to its deliverable: reference personality, full command/field semantics, fixed-point defaults and units, 43 diagnostic signatures, 48 source-defined cases, nine characterization cases, and independent MIT provenance/dependency disposition. The 21-item findings register preserves bugs rather than replacing them with fixes. Completion means the specification/data and static checks exist, not that runtime compatibility has passed or that implementation is approved.

2. **▧ Transport, registry, and persistence.** After explicit approval, implement original Linux/PTY handling and firmware-like parsing/EEPROM/device actions. Execute source-defined wire fixtures, including malformed/partial input, live-versus-saved settings, ownership, duplicate handling, query quirks, and exact frame/type/byte cases. Keep characterization obligations visible and unqualified until required reference evidence exists. No invented error, rollback, discovery sorting, or extra telemetry may substitute for source behavior.

3. **▧ Controller and thermal environment.** Independently implement matching sensor/filter/PID/state/timer actions against controlled input histories, with documented AVR-width/rounding effects and deterministic bugs. Execute semantic vectors for filter routing, derivative sign, integral evaluation count, minimum-on boundaries, and camera test mode. Separately validate physical energy balance, heat-source signs, beer/chamber lag, and endogenous fermentation heat. Compare identical simulated-time inputs at 1x/10x/60x; correct dynamics and plausible plots are not proof of reference-controller equivalence.

4. **▧ Actual host/panel integration.** Run isolated pinned host/panel processes with their own configuration, sockets, logs, and web data. Complete n then s/c/v startup; use E through the normal panel reset to initialize an erased controller store; discover/assign probes and actuators, change beer targets, and observe firmware-like states and evolving physical temperatures. Verify LCD bytes/alternation, units, maintenance/default actions, profile disabled segments, reset/rediscovery, and restart with what the firmware actually saved. Use socket/harness checks for calibration/deactivation/manual writes where UI controls are absent. Label each operation by the interface actually used and do not claim another external panel's compatibility.

5. **▧ Target qualification and operating guidance.** On an agreed Pi/Linux target, verify PTY ownership/service readiness, native build/toolchain, response behavior under the reference's blocking paths, restart, checkpoint coherence, and achieved acceleration/backpressure. Retain exact reference-artifact evidence for affected characterization cases before claiming parity. Document actual commands and limitations, inspect original MIT/provenance and actual dependency/build/package contents, and keep source review/native Linux/host-panel/Pi/Arduino evidence separate. Physical controller work, deployment, releases, and distribution remain separately scoped actions.

## Material risks and review boundary

- Firmware fidelity intentionally includes incorrect, stale, or partial results. Earlier cleaner semantics are withdrawn; no silent fix is permitted when source behavior is known.
- Undefined stack/memory, extreme AVR arithmetic, and physical bus/pin-history cases require the exact reference artifact and initial state. They have no fabricated passing oracle and remain compatibility-evidence gates for affected claims.
- Legacy host dependencies may require a suitable isolated environment; do not silently modernize reference repositories as emulator work.
- The selected normal firmware identity exposes hardware-oriented panel controls. Programming/USB hardware flows are not implemented by the emulator, and no actual flashing belongs in ordinary checks.
- Controller storage can differ from current live values by design. Do not promise persistence of every accepted mutation or atomically durable source behavior that the reference lacks.
- Independent MIT authorship does not authorize porting code or establish formal clean-room separation. Newly incorporated dependencies, generated outputs, and any future captures/packages need the provenance review.
- The exact Pi model/OS and any panel other than brewpi-www-rmx remain qualification inputs. These do not justify leaving known serial semantics unspecified or changing firmware behavior.

The reviewed milestone 1 artifacts and static checks are the current deliverable, with their commit and push to main authorized by the owner. No emulator/parser/controller/persistence implementation, executable harness, build system, reference execution, or device operation is authorized by this publication task. Implementation requires a subsequent explicit instruction.
