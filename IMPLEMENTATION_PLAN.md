## Scope and governing decision

Build an independent native C++ Linux application that replaces the Arduino for hardware-free BrewPi integration testing. Use the reference repositories to describe externally observable communications and controller characteristics; do not copy, vendor, link, translate, or otherwise reuse their implementation code. This incorporates the user's clarification during this review and supersedes HANDOFF.md requirement 9's suggestion to reuse PID, filtering, and state-machine code. HANDOFF.md remains the original handoff record.

Original emulator code, tests, tools, fixtures, configuration examples, and documentation use MIT under [LICENSE.md](LICENSE.md), with the owner's 2026 Lee Bussy notice and additional contributor notices retained as applicable. New original source/helper files must carry an MIT SPDX identifier where their format permits it; other formats may use an adjacent record. Third-party components retain their own terms and must not compromise the independent MIT implementation boundary; record their actual incorporation and notices separately. No reference source may be incorporated merely because a license notice has been added. The [contract](CONTRACT.md) governs scope/licensing, and the [provenance review gate](engineering/licenses/README.md#review-gate) defines the shared authorship, dependency, generated-output, and distribution checks.

Independence applies to every emulator component, including protocol parsing/serialization, controller logic, filters, thermal modeling, device management, persistence, and test helpers. Record behavioral facts in a specification, then author original code and tests from that specification; do not transplant source structure, algorithms expressed as code, headers, macros, generated tables, or test implementations. Required wire names, enum values, field types, timing characteristics, and independently authored example messages are compatibility facts and may be recorded. This is source-informed independent development, not a claim of a formally separated clean-room process. General-purpose dependencies such as a JSON library are permitted, subject to their own licenses; no BrewPi/Fuscus implementation is an emulator dependency. Unmodified host and panel processes remain permitted external integration-test clients, resolving the distinction between code reuse and testing compatibility with existing software.

Automated or AI-assisted translation, paraphrasing, renaming, or restructuring of reference implementation is also prohibited. Standard scientific equations, conventional algorithms implemented independently, and common repository conventions remain permitted. Original test vectors must be authored from the behavioral specification; raw external captures or diagnostic prose are not automatically MIT material. Select permissively licensed incorporated general-purpose library code; record external toolchain/system-library/client versions by their actual role and reassess any future bundling separately.

The first supported system is one chamber containing a carboy with five US gallons of beer, using brewpi-script-rmx and brewpi-www-rmx on the same Raspberry Pi/Linux host. Success means real startup, sensor and actuator assignment, control changes, credible evolving temperatures, and persistent settings through the existing panel. Exact firmware arithmetic, PID qualification, USB device emulation, GPIO, physical peripherals, firmware flashing, and other panel implementations are outside the initial scope.

## Source-backed compatibility review

### Startup, transport, and host timing

The host accepts an explicit serial path through `serial.serial_for_url`; USB discovery is only used when the configured port is `auto`. It opens at 57600 baud with one-second read/write defaults, clears its buffers, waits `startupDelay` seconds (default 10), requests `n`, and then starts background serial processing and requests `s`, `c`, and `v`. Version acquisition uses one-second reads and retries within its approximately ten-second search. Sources: [serial setup](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/BrewPiUtil.py#L376), [startup](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L724), and [version acquisition](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpiVersion.py#L43).

Commands can be single bytes without newlines, although the background client normally appends a newline. Object-bearing commands use firmware's permissive JSON-like syntax, including unquoted keys such as `j{mode:"b",beerSet:20}` and `h{u:-1,v:1}`; a strict JSON-only input parser would fail. Responses use a case-sensitive character prefix, colon, JSON payload, and newline; emit CRLF for compatibility with firmware output. Whitespace between commands is ignored. Implement bounded incremental parsing that handles fragmented and coalesced writes, strict JSON from the panel, and the host's flat unquoted-key objects. Do not duplicate firmware's blocking token parser or its unsafe edge cases. Sources: [command dispatch](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L136), [parser](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L688), and [background client](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/backgroundserial.py#L46).

Use ASCII for structural output and JSON escapes for non-ASCII text because the host decodes serial as CP437. The LCD degree cell must remain one decoded character at column 18, not a multi-byte UTF-8 glyph. Accept signed/decimal numbers, quoted numeric values, strings, booleans, and null where the relevant setting allows them; null is required for disabled profile segments. Keep object member order for mixed unit/temperature writes because firmware applies pairs sequentially. Proposed bounds are a 4 KiB command and a one-second wall-clock inter-byte timeout; reject nested objects/arrays and unsupported keys without desynchronizing subsequent commands. Recover malformed or timed-out objects at a newline or a completed discard boundary rather than interpreting their remaining bytes as standalone commands. These bounds and whole-command validation are intentional robustness differences, not firmware parser emulation.

The host checks serial while servicing its socket at roughly 0.5-second intervals, requests LCD content around every five seconds, refreshes settings after roughly 60 seconds, and requests temperatures using its configured logging interval (default 120 seconds). Its counters also contain five-second retry increments, so preserve responsiveness rather than assuming a perfectly periodic schedule. Proposed acceptance budget: complete replies within 250 ms of a complete request under normal local load, independent of simulation speed, including while paused. Sources: [polling](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1483) and [defaults](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/settings/defaults.cfg#L8).

### Command and response contract

| Command | Response or effect | Initial coverage |
| --- | --- | --- |
| `n` | `N:{...}` identity | Required for startup; reply on every request. |
| `t` | `T:{...}` temperatures, setpoints, annotations, and state | Full ordinary telemetry, including null/disconnected values. |
| `s`, `c`, `v` | `S:{...}`, `C:{...}`, `V:{...}` | Settings, constants, and diagnostic variables used by maintenance. |
| `j{...}` | Apply settings; send `S` and `C`; relevant `T` annotations | Modes, setpoints, units, controller constants, filters, and estimators. |
| `S`, `C` | Restore default settings or constants, respectively, and report them | Preserve distinction from lowercase reads; mirror affected scope. |
| `l` | `L:[line0,line1,line2,line3]` | Four padded 20-character display lines; host indexes character 18 of lines 1 and 2. |
| `h{...}` | `h:[...]` hardware inventory | Honor `h` hardware, `p` pin, `v` values, `u` unused, and `f` assignable-function filters. |
| `d{...}` | `d:[...]` installed slots and optional readings or actuator writes | Honor `i` slot, `e` empty slots, `r` reads, `w` writes, and camera-light index `i:-2`; the camera-light special case returns `d:[]`. |
| `U{...}` | `U:{...}` resulting installed device | Apply, edit, deactivate, or remove assignment; invalid input leaves prior assignment intact. |
| `E` | Initialize controller settings and devices; diagnostic message | Factory reset of emulated controller configuration; refresh with `s/c/v/d/h`, since firmware does not send all readbacks automatically. |
| `R` | Controller reboot | Reset volatile controller state, retain saved settings and stable identities, keep PTY available. |
| `A`, `a` | Alarm on/off | In-memory alarm only. |
| `y{...}`, `Y` | Firmware simulator configuration/readback | Defer legacy simulator dialect; use emulator CLI/scenario controls initially. |
| `e`, `Z` | Optional EEPROM dump/debug erase | Defer; not used by the normal host/panel workflows reviewed. |

The dispatch and output source of truth is [PiLink.cpp](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L136). The host sends the actual discovery, update, reset, and write commands in [brewpi.py](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1097). Verify deferred commands are absent from the selected acceptance workflow before declaring compatibility. Firmware upload is a separate host programmer workflow and cannot be implemented by responding to a serial command.

`T` will use full names: `BeerTemp`, `BeerSet`, `BeerAnn`, `FridgeTemp`, `FridgeSet`, `FridgeAnn`, `State`, and `RoomTemp`. Temperatures/setpoints are JSON numbers or null, annotations are strings or null, and state is an integer. The host also recognizes compact simulator names, but full snapshots avoid delta-cache ambiguity on reconnect. Ordinary firmware omits `RoomTemp` when disconnected; this emulator deliberately sends `RoomTemp:null` when absent so the host's merged cache clears a previously valid room reading. Never send NaN, Infinity, or the string `"null"`. Sources: [telemetry output](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L296) and [host cache merge](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1521).

| Response | Exact fields and JSON types |
| --- | --- |
| `S` | `mode` string; `beerSet` and `fridgeSet` number or null; `heatEst` and `coolEst` number. |
| `C` | `tempFormat` string; every remaining field is a JSON number: `tempSetMin`, `tempSetMax`, `pidMax`, `Kp`, `Ki`, `Kd`, `iMaxErr`, `idleRangeH`, `idleRangeL`, `heatTargetH`, `heatTargetL`, `coolTargetH`, `coolTargetL`, `maxHeatTimeForEst`, `maxCoolTimeForEst`, `fridgeFastFilt`, `fridgeSlowFilt`, `fridgeSlopeFilt`, `beerFastFilt`, `beerSlowFilt`, `beerSlopeFilt`, `lah`, and `hs`. Filter coefficients, time limits, `lah`, and `hs` are integers. |
| `V` | Numbers for `beerDiff`, `diffIntegral`, `beerSlope`, `p`, `i`, and `d`; numbers or null for temperature-valued peak fields `estPeak`, `negPeakEst`, `posPeakEst`, `negPeak`, and `posPeak`. |

The earlier plan incorrectly described formatted numeric buffers as numeric strings on the wire. `sendJsonPair(const char*)` prints those buffers without quotes; the host directly compares parsed constants with numeric setpoints. Preserve JSON numbers even when the serializer uses an intermediate text representation. Match meaningful precision: `T` temperatures and `S` setpoints use two decimal places, absolute `C` limits use one, and most differences/factors and `V` values use three. Whitespace padding and bit-identical fixed-point rounding are not acceptance requirements. Sources: [settings output](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L487), [output maps](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L505), [unquoted numeric emission](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L666), and [host numeric comparisons](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L917).

Accept all `S` and `C` fields as `j` inputs, with their exact wire names, and treat `V` fields as read-only. Convert absolute temperatures with the C/F offset, temperature differences/slopes/estimators with scaling only, and dimensionless gains/filter indices/times without temperature conversion; changing units must not change the physical plant or canonical setpoints. Specify the firmware's field-specific conversion categories in milestone 1, including the fixed-point PID contribution fields. Accept null for beer/fridge setpoints but reject it for numeric gains/timers. Unknown, malformed, or out-of-range mutations leave the prior state intact; report a supported `D` error plus unchanged `S/C` or `U` readback where applicable. This validation is deliberately stricter than firmware's partial-pair application. A valid ordered `j` object commits as one durable transaction, then emits final `S/C` and relevant annotations; do not expose partially committed settings.

Unsolicited controller output includes a full `T` on every controller state transition, `T` annotations for control/door changes, and `D:{"logType":...,"logID":...,"V":[...]}` diagnostic records; settings changes also produce settings/constants readback in ordinary firmware operation. Without transition telemetry the default 120-second host poll can miss important changes. Keep application logs on stderr or journald, never on the PTY. Independently serialize the required diagnostic subset using the compatible numeric IDs, `I/W/E` types, and argument ordering established in the behavioral specification; do not copy source enums or diagnostic text tables. The host separates `D` records from ordinary replies and already owns message expansion. Sources: [state-transition telemetry](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Brewpi.cpp#L130), [settings reception](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L750), [logger](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Logger.cpp#L42), and [host diagnostic expansion](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/expandLogMessage.py#L71).

### Identity and device schemas

Protocol identity is `N` with `v` (parseable firmware compatibility version), `n` (build name), `s` (numeric shield), `y` (numeric simulator flag), `b` (board character), and `l` (log-message version, emitted as a string by firmware). The host also optionally reads `c` as commit metadata. Proposed initial identity is `N:{"v":"0.2.13","n":"brewpi-emulator-rmx","s":2,"y":1,"b":"s","l":"3"}`. Version `0.2.13` is the nearest tag returned by the reviewed firmware checkout's version-generation command; it denotes the targeted protocol family, not a claim to run that firmware or implement every optional command. Record the emulator's own release/build metadata separately and omit `c` until an emulator revision exists. The Uno/RevC personality and simulator flag are explicit compatibility declarations. The reviewed host uses `y` for identification, not to request `y/Y` simulator commands or require compact telemetry. Sources: [identity output](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L190), [version generation](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/tools/git_rev.py#L30), [identity interpretation](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpiVersion.py#L84), and [host minimum](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L86).

The known board/shield pair matters: the host builds the panel's pin list from it; an unknown board character produces an empty pin list. Uno/RevC provides OneWire bus 18, actuator pins 6, 5, 2, and 19, and door pin 4. The panel displays OneWire addresses and uses slot, function, pin, hardware, and ownership fields when applying assignments. There is no controller-unit serial-number field in the reviewed `N` response. Store a stable emulator instance ID in local metadata, and use the stable path plus sensor addresses for instance distinction. Sources: [pin mapping](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/pinList.py#L61), [host device response](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1108), and [panel device UI](https://github.com/brewpi-remix/brewpi-www-rmx/blob/f79631830a99575e250403f08a19be8bf944596c/js/device-config.js#L171).

Device records contain `i` (slot), `t` (type), `c` (chamber), `b` (beer), `f` (function), `h` (hardware), `d` (deactivated), and `p` (pin), plus `x` (pin inversion), `a` (OneWire address), `j` (temperature calibration adjustment), and optional `v` (reading) where applicable. Slots are 0–15; discovered uninstalled hardware must retain firmware's `i:-1` unassigned-slot convention rather than acquire a permanent slot from enumeration order. Types are 0 none, 1 temperature, 2 switch input, and 3 switch output; hardware 1 is a digital pin and 2 is a OneWire temperature sensor. Functions are 0 none, 1 door, 2 heater, 3 cooler, 4 light, 5 chamber temperature, 6 room temperature, 7 fan, and 9 beer temperature. Chamber devices use chamber 1 and beer 0; the beer sensor uses chamber 1 and beer 1. Addresses are eight bytes printed as 16 uppercase hexadecimal characters without separators. Sources: [enums](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.h#L58), [device formatting](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L573), and [device documentation](https://github.com/brewpi-remix/brewpi-userdocs-rmx/blob/bc8704c40b09afbc5d3d8df2df04cc7ed358c9ba/docs/devices/index.rst#L25).

Provide three stable synthetic DS18B20-family (`28`) addresses with valid Dallas CRC bytes, distinct per configured emulator instance and fixed before first exposure. Bind each physical virtual probe to beer, chamber, or room in scenario configuration; assigning a probe to another function changes what the controller reads, not its physical location. Keep addresses distinct from editable slot IDs. Start with discovered hardware but no assignments, matching the documented fresh-controller workflow. Discover the RevC virtual pin inventory, support logical actuator read/write and inversion metadata, and keep actual GPIO absent. DS2413 and secondary beer functions are deferred even though some enums/UI options mention them; current firmware comments out DS2413 implementation. Sources: [hardware discovery](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L814) and [fresh configuration](https://github.com/brewpi-remix/brewpi-userdocs-rmx/blob/bc8704c40b09afbc5d3d8df2df04cc7ed358c9ba/docs/devices/index.rst#L7).

For `h`, defaults are `h:-1,p:-1,v:0,u:0,f:0`: all hardware/pins, no values, include assigned hardware, and no function restriction. Any nonzero `u`, including host value -1, requests unassigned hardware only. Assigned records carry their installed slot/configuration; unassigned probes use `i:-1`, `c:1`, `b:0`, `f:0`, `h:2`, `t:0`, their bus/address, and calibration 0. The returned `t` is derived from assigned function, not the physical probe type. Readings requested by `h{v:1}` are raw, uncalibrated probe values; installed `d{r:1}` reports calibrated probe values, not the filtered `T` measurement. For `d`, defaults are all slots (`i:-1`), no reads/writes, and omit empty slots (`e:0`); `e:1` includes empty slots, while a specific valid `i` returns that slot even if empty. A `w` write takes precedence over `r` and is followed by a separate read to verify state. Sources: [hardware matching/readback](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L698), [query defaults](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L886), and [installed reads/writes](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L927).

`U` is a patch to the specified slot: preserve omitted fields, derive output-only `t`, clear the complete slot when `f:0`, and accept deactivation/calibration through `d`/`j`. Require slots 0–15, correct ownership, assignable hardware, known virtual pins/probes, and no conflicting assignments; explicitly reject slot 16 despite the reference input-boundary inconsistency. Return the resulting record on valid updates or the original record after rejection of an addressable slot; invalid indices produce a diagnostic without a fabricated record. Commit the registry before `U`, because the panel immediately follows Apply with discovery refresh and the host requires both `d` and `h` to mark its cache current. Explicit ROM addresses are the supported initial assignment form; the legacy all-zero “first on bus” alias is deferred and rejected clearly, since the panel renders it as text unsuitable for an ordinary address round-trip. Sources: [slot patch behavior](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L394), [panel Apply/refresh](https://github.com/brewpi-remix/brewpi-www-rmx/blob/f79631830a99575e250403f08a19be8bf944596c/js/device-config.js#L532), and [host cache readiness](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1097).

Discover the three probes and four actuator pins initially. RevC defines door pin 4, but ordinary hardware enumeration only includes sensor pins when `BREWPI_SENSOR_PINS` is enabled; expose the door through a documented direct assignment/scenario test rather than silently asserting it is auto-discovered. Calibration and deactivation are supported protocol features, but their setters are commented out in the reviewed panel's configuration serializer; exercise these with the host socket or protocol harness. Manual actuator test writes likewise belong in the harness unless a current panel control is identified. The panel can discover, assign, read, and remove devices, and edit maintenance settings; do not make unsupported UI interactions an acceptance prerequisite. Sources: [enumeration gates](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L780), [sensor-pin default](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/ConfigDefault.h#L96), and [panel serializer](https://github.com/brewpi-remix/brewpi-www-rmx/blob/f79631830a99575e250403f08a19be8bf944596c/js/device-config.js#L545).

### Existing simulator and Fuscus assessment

The firmware simulator already models beer heat capacity from volume and density, chamber air plus cabinet thermal mass, beer/chamber and chamber/room conduction, heater/cooler watts, a daily room-temperature curve, and fermentation heat. It advances in one-second steps and runs temperature updates, peak detection, PID, state transitions, and outputs before thermal evolution. These are useful behavioral references for an independent model; the default beer volume is 20 liters, so it does not directly satisfy the requested five-gallon scenario. Sources: [thermal model](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Simulator.h#L88) and [simulation loop](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Simulator.cpp#L99).

Do not reproduce its limitations: fermentation heat has discontinuities and can exceed its named maximum just after day 2; door losses are a stub; the cabinet-mass comment and actual value disagree; noise is one-sided; quantization helpers are not used by the sensor-update path; and room temperature is not explicitly initialized before every possible sensor update. More importantly, `BREWPI_SIMULATE` suppresses OneWire discovery, auto-installs sensors, switches to compact/delta telemetry, and suppresses the ordinary `S`/`C` replies after `j`. Its simulated `oneWireBus` also returns null while assignment validation expects a non-null bus. The independent emulator must support the normal panel workflow rather than inherit these simulation-build choices. ## Proposed independent design

### Boundaries and build

Use C++17, CMake, a system C++ compiler, and POSIX/Linux APIs. Use `posix_openpt`, `grantpt`, `unlockpt`, termios, and poll for transport, avoiding a mandatory socat daemon or Arduino toolchain. Propose a pinned, permissively licensed JSON library for strict output and scenario/state files, with a small independently written bounded parser for the host's flat command objects. Python 3 and pyserial are proposed external test-harness tools; the existing BrewPi stack retains its own dependencies. No library/tool versions have been selected or incorporated yet. Native Linux x86_64 and Raspberry Pi ARM64 are proposed initial build targets; ARM32 is a separate compatibility check if needed. macOS may support development checks but does not qualify Linux PTY/service behavior.

| Module | Responsibility and interface |
| --- | --- |
| Serial transport | Own PTY, stable symlink, byte buffering, partial writes, client disconnects, and wall-clock request deadlines. |
| Protocol adapter | Parse commands, serialize exact schemas, dispatch configuration changes, and emit asynchronous annotations. |
| Device registry | Own stable inventory and mutable slots; map probe readings and logical outputs to assigned functions. |
| Controller | Independently implement modes, filtering, PID-style chamber target, peak estimates, timed states, and actuator decisions. |
| Thermal plant | Advance beer/chamber temperatures from applied virtual actuator power and scenario conditions; expose room temperature separately. |
| Simulation clock | Own elapsed simulated time, fixed steps, acceleration, pause, and deterministic scheduling. |
| Persistence/scenarios | Load validated initial conditions, store controller configuration/identity, and optionally checkpoint coherent plant/controller state. |

No Arduino adapter layer, AVR sources, firmware binaries, firmware libraries, or Fuscus modules will be build inputs. Existing components are not directly native-ready in any event: Platform.h includes Arduino.h, main.cpp uses AVR watchdog registers, and device creation accesses pins and OneWire. Those observations explain why a firmware native port would be a different project; it is not this implementation strategy. Sources: [platform dependency](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Platform.h#L32), [AVR entry point](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/main.cpp#L30), and [hardware creation](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L89).

### Controller characteristics

Implement `o` off, `f` fridge constant, `b` beer constant, `p` host-driven beer profile, and `t` manual device test. Off clears active setpoints and automatic heater/cooler demand; door/camera-light behavior remains separate. Fridge constant uses the chamber target directly and disables the beer setpoint; beer modes derive a bounded chamber target from beer error, smoothed slope, and an integral with anti-windup. Profile scheduling remains in BrewPi, including null setpoints during disabled segments. Use independently designed numeric/filter classes; approximate source behavior and document numerical differences rather than translate fixed-point filter or PID routines. Every supported thermal/control parameter must change its associated behavior. `hs` is an explicit stored/readback-only exception because rotary hardware is absent; do not claim it affects thermal control. `lah` affects light demand, and light heat affects the plant only when its configured physical load has nonzero power. Sources: [modes](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/ModeControl.h#L40), [PID characteristics](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L160), [outputs](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L435), and [host profile updates](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1777).

Preserve state numbers 0 idle, 1 off, 2 door-open display state, 3 heating, 4 cooling, 5 waiting to cool, 6 waiting to heat, 7 waiting for peak detection, 8 minimum cooling time, and 9 minimum heating time. Model ordinary non-glycol timing: 300-second heat/cool minimum off times, 180-second minimum on times, 600-second heat/cool switching delay, and 600-second cooling off time in fridge-constant mode. Include startup waiting, hysteresis, overshoot/peak waiting, unavailable-sensor handling, and test-mode actuator writes. These are simulated seconds. In automatic control, heating and cooling demand are mutually exclusive; this is not a guarantee about physical loads under intentionally incorrect wiring/inversion. Device-test behavior follows explicit writes and is recorded as such. Route demand through the assigned pin and its inversion/load polarity before deriving physical heater/cooler power, so missing or deactivated actuators have no heating/cooling effect. Sources: [states and timings](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.h#L43), [transitions](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L244), and [output behavior](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L435).

Do not infer telemetry state solely from mode: reference `updateState` can report IDLE (0) in off mode after disabled-setpoint checks. Door-open state 2 overrides the LCD display, while `T.State` carries the controller's underlying state. In test mode, preserve commanded output latches across controller ticks; outside test mode, automatic control overwrites manual writes on the next tick. All mutations still work while paused, but simulated timers and automatic evolution wait for the next tick. Define startup/filter initialization from current valid probe values, and enforce immediate logical heater/cooler shutdown in automatic modes when a required probe or assignment disappears. Implement the camera-light request's 600-second simulated auto-off separately from ordinary manual output latches. Sources: [state precedence](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L254), [display versus telemetry state](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.h#L259), [test-mode output handling](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L437), and [camera-light timeout](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L62).

Bind virtual loads to physical virtual pins, just as probes bind to physical locations. Proposed scenario wiring is heater on pin 5, cooler on pin 6, light on pin 2, and fan on pin 19, with shield inversion defaulting to 1. Function assignment routes controller demand to a pin and must not redefine that pin's load. Track logical active state, inverted electrical level, and configured load polarity separately; wrong assignment or inversion should have observable consequences rather than silently changing the simulated wiring. Unassigned/deactivated loads are explicitly quiescent in this hardware-free model. This is a deliberate boundary rather than an attempt to simulate floating relay inputs. Do not count one physical load twice when `lah` routes demand to both heater and light functions. Source: [logical/electrical inversion](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/ActuatorPin.h#L47).

### Thermal model and clock

Use an independent two-body energy balance with a separately tracked room boundary: `Cbeer*dTbeer/dt = Qfermentation + Kbeer*(Tchamber-Tbeer)` and `Cchamber*dTchamber/dt = Qheater-Qcooler+Qauxiliary + Kbeer*(Tbeer-Tchamber) + Kroom*(Troom-Tchamber)`. `Qauxiliary` is any configured light/fan heat from active physical loads, zero by default. Count each physical load once. Beer capacity includes 18.927 liters of beer and configurable carboy heat capacity; chamber capacity includes air and configurable cabinet contents. Room temperature is a configured constant or deterministic daily curve, representing a large surrounding reservoir. A finite room energy model is unnecessary for this initial scenario. Keep internal units in Celsius, joules, seconds, and watts.

Proposed starter parameters, subject to scenario validation: 400-liter chamber, 20 C initial beer/chamber/room, 25 W heater, 60 W cooler, 3 W/K beer/chamber coupling, and 1.67 W/K chamber/room coupling. Use 1000 kg/m³ beer density and 4180 J/(kg·K) specific heat, add 6000 J/K carboy capacity, and use 2000 J/K cabinet capacity plus chamber air capacity; all are configurable. These are illustrative simulation inputs informed by the reference simulator and ordinary energy balances, not measured refrigerator properties. Light/fan loads default to zero additional watts, with optional heat contributions through the physical load map. Provide fermentation-off and active-fermentation scenarios; use a continuous, bounded lag/ramp/peak/decay heat curve with configurable maximum watts and fermentation age. Default noise is zero; optional seeded symmetric noise and 0.0625 C sensor quantization apply at the probe boundary. Probe lag is separate from physical thermal inertia and controller filtering. Calibration adjusts the probe measurement, not the plant temperature, and is interpreted as a temperature difference in the current wire units.

Advance the controller on one-second simulated ticks and integrate the plant at fixed steps of at most one second, subdividing if scenario parameters require it. Use a monotonic wall clock to schedule ticks; acceleration changes tick frequency, never integration step length or control timers. Process serial between bounded batches to avoid starvation. Compare equal simulated-time runs at 1x, 10x, and 60x; add a deterministic headless stepping mode for long scenarios. Pausing freezes simulated dynamics but leaves serial replies available. Reopening the port does not reset the plant.

Define one deterministic tick order: sample the current plant into connected probes, apply calibration/lag/quantization and filters, update controller demand/state and physical outputs, then integrate the plant for the next second. Schedule scripted inputs by simulated time, with an explicit order for inputs on tick boundaries. Use bounded output queues and prioritize requested replies; if a connected reader cannot drain transition telemetry, slow simulated advancement and report achieved speed rather than silently drop requested responses or grow memory indefinitely. With no client, retain current state rather than queue an unlimited history; the next requested `t` is a full snapshot. Include this backpressure case in acceleration tests.

BrewPi fermentation-profile interpolation, polling, CSV dates, and chart dates use host wall time; an emulator speed factor cannot accelerate them. At 60x, one wall minute represents one simulated hour of plant/controller response, while the host profile advances one minute and charts retain wall timestamps. Default panel testing is therefore 1x; acceleration is for constant-setpoint exploration and emulator-owned scripted scenarios. Record both clocks in emulator diagnostic artifacts without changing host timestamps or the operating-system clock. A synchronized accelerated host-profile harness is deferred. Sources: [profile wall clock](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/temperatureProfile.py#L45), [chart timestamps](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpiJson.py#L64), and [CSV timestamps](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1681).

### Persistence and Linux integration

Use a versioned JSON configuration/state format with atomic replacement, validation, and explicit failure for corrupt or unsupported state. Persist instance identity, probe addresses, slots/assignments, mode, setpoints, units, controller constants, and estimators. Persist accepted configuration changes before confirming them; on storage failure retain the prior live configuration, return unchanged readbacks where applicable, and log the failure. By default, a process restart reloads saved configuration with the configured initial thermal conditions and reset volatile filters/timers. An explicit checkpoint/resume option restores a coherent snapshot of configuration, plant temperatures, fermentation age, elapsed time, probe/filter histories, controller integrator/peak state, timer epochs, output latches, and random state. Resume adds no elapsed downtime automatically. A plant-only restore must be labeled as such and cannot claim trajectory continuity. Label both restart policies clearly. `R` reboots only the controller while the plant continues, resets its timing epoch/filters and output latches, and reloads durable configuration; it does not advance fermentation age or replace the PTY. `E` clears controller assignments, restores default settings/constants and controller timing, retains physical plant/scenario state and probe/instance identities, and leaves the registry initialized so immediate `d/h/U` works. A separate explicit scenario reset restores repeatable initial conditions.

Propose a configurable stable path such as `/run/brewpi-emulator/chamber1/serial`, owned by the BrewPi service account, with an instance lock and atomic symlink replacement. Keep the PTY slave raw, suppress echo, and handle no-client/EIO conditions without exiting. Refuse to replace an unrelated file or another active instance's link. Create the endpoint before the host starts and document restarting the host after emulator process replacement, since an already-open PTY descriptor does not migrate when a symlink changes. Verify permissions as the actual host user and clean up only owned runtime files.

The smallest host integration is configuration: `port = /run/brewpi-emulator/chamber1/serial`, `altport = None`, and optionally `startupDelay = 0`. No host or panel source change is expected for the core scenario. USB `auto` discovery matches VID/PID, and the installer normally creates udev links from USB serial descriptors; a PTY supplies neither. For an existing installation, configure the path directly and skip USB pairing; for future installer support, add a separate explicit emulator-port selection rather than fake USB metadata. A future service template should follow the existing per-chamber service/user convention, order the host after endpoint creation, and use persistent state outside `/run`. Sources: [USB detection](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/autoSerial.py#L38), [installer pairing](https://github.com/brewpi-remix/brewpi-tools-rmx/blob/7e95e19796bed3e8cd6aa08f08f89db05ac66fa4/install.sh#L458), and [service convention](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/utils/doDaemon.sh#L180).

## Material risks and review decisions

- **Independent behavioral fidelity:** PID/filter/peak behavior will approximate the reference rather than reproduce its fixed-point arithmetic. The compatibility boundary is real protocol/workflow support and plausible reactive behavior; document numerical differences and do not claim controller qualification.
- **Legacy host environment:** the host imports legacy Python packages/APIs and may need an appropriate isolated runtime on the selected Pi OS. Diagnose that separately from emulator protocol failures; do not silently modernize reference repositories as part of emulator work.
- **Panel identity and programming:** the Uno/RevC personality enables the existing device UI but also exposes hardware programming UI. Firmware flashing remains unsupported; the operator guide must identify it, and any future UI disablement is a separately reviewed integration change. No automatic flashing action belongs in acceptance tests.
- **Persistence differences:** persisting every accepted setpoint intentionally differs from AVR EEPROM wear-saving behavior in profile mode. Atomic storage failure must be visible rather than acknowledged as durable success.
- **Device validation:** some reference uniqueness checks are TODOs. Independently reject contradictory duplicate probe/pin/function assignments with the original assignment retained; document this stricter behavior rather than reproduce memory hazards.
- **External panel clarification:** brewpi-www-rmx is the reviewed panel. Any additional “external control panel” needs its name, version, interface, and required workflows before compatibility can be promised; this does not block the proposed BrewPi reference-panel milestone.
- **Target decisions:** confirm Pi model, OS, ARM64 versus ARM32 needs, and whether a different emulated shield personality is required before implementation packaging. Proposed defaults are one chamber, Uno/RevC, ARM64 Linux, 1x panel use, and explicit optional checkpoint resume. The license decision is resolved: original project work uses MIT.
