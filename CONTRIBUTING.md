# Contributing

Read the [project contract](CONTRACT.md), [implementation plan](IMPLEMENTATION_PLAN.md), and [development guide](engineering/development/README.md) first. The public repository is [brewpi-remix/brewpi-emulator-rmx](https://github.com/brewpi-remix/brewpi-emulator-rmx), with `main` holding the reviewed project baseline. Local Git is initialized, and `origin` uses the repository's HTTPS URL. Milestones 1–5 are published, including six native suites, opt-in isolated host/panel integration, selected Linux qualification, and operating guidance. After review, the owner authorized committing and pushing the reviewed cross-milestone fixes, tests, and supporting docs to main, preserving Arduino behavior and independent MIT licensing. No automated CI exists.

Base documentation contributions on `main` and target `main` in pull requests. No separate development branch, branch-protection policy, automated merge policy, or release process has been established. Further milestone work remains subject to an explicit user instruction; the owner authorized the reviewed milestone 2 commit and push to main, while milestone 3 was subsequently authorized for implementation/validation with a stop before commit/push. After review, the owner authorized committing and pushing milestone 3 and its supporting artifacts to main. The owner subsequently authorized isolated milestone 4 integration, with a stop for review before committing or pushing. After review and fixes, the owner authorized committing and pushing milestone 4 and its supporting artifacts to main. The owner subsequently authorized milestone 5 qualification and operating guidance using isolated Debian 12 ARM64 Linux, stopping for review before committing or pushing. After review and fixes, the owner authorized committing and pushing the reviewed milestone 5 target qualification, operating guidance, tests, and supporting docs to main, preserving Arduino behavior and independent MIT licensing. Physical-device work, releases, and deployment remain unapproved.

Follow the [firmware behavioral contract](engineering/protocol/behavioral-contract.md), including documented bugs. When uncertain, preserve the Arduino action/reaction and record a finding rather than improve validation, persistence, output, or control behavior. Required interoperability facts and original fixtures remain compatible with independent authorship; copying or translating implementation is still prohibited. Do not count characterization-required cases as passing conformance checks.

Contribute original work under the [MIT License](LICENSE.md). Do not import or translate reference implementation code, tests, tables, or assets. Describe the relevant behavioral contract and author changes independently. Record any new general-purpose dependency and its license in [third-party notices](THIRD_PARTY_NOTICES.md) before adding it.

By intentionally submitting an original contribution for inclusion, you agree to license that contribution under this project's MIT License and confirm you are entitled to do so. Preserve existing copyright notices and identify additional contributors' notices as appropriate; the owner's root notice does not replace them. Include `SPDX-License-Identifier: MIT` on new original source/helper files, using an adjacent record for formats that cannot carry comments. Do not submit reference-derived work through an automated translation or an AI-assisted rewrite.

For a future code/dependency change, state whether material was independently authored, which behavioral specification it implements, and whether any third-party bytes, generated assets, or captures are included. Complete the [provenance review gate](engineering/licenses/README.md#review-gate) and actual dependency inventory before introducing them. Contribution templates record this statement; no signed CLA or DCO process has been established.

Keep changes focused, preserve unrelated work, and update documentation when behavior or supported scope changes. Follow `.editorconfig` and `.clang-format`; use one physical line per prose paragraph or prose list item and Oxford commas. Do not include credentials, generated runtime state, private captures, or new machine-specific paths in shared guidance.

A change description should explain the problem, resulting behavior, validation performed, and material limitations. Distinguish source review from execution, and Linux host evidence from Raspberry Pi qualification. Do not claim a passing build or test suite until those facilities exist and have actually run.

The owner authorized repository creation, Git initialization, and the initial documentation/scaffolding commit and push to `main`. Subsequent implementation, commits, pushes, releases, and deployment follow the scope of the active task; this initial publication does not approve emulator implementation.
