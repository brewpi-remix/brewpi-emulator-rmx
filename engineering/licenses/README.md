# Authorship and component provenance

Original implementation, tests, fixtures, helpers, scenarios, and prose use the root [MIT License](../../LICENSE.md). Behavioral specifications record interoperability facts; they do not license reference implementation code for reuse. Source exposure is disclosed, and no formal clean-room separation is claimed.

Do not copy, vendor, link, translate, adapt, mechanically rewrite, or AI-rewrite BrewPi/Fuscus implementation, headers, routines, generated tables, tests, or assets. Standard equations and independently implemented conventional algorithms are permitted. MIT labeling alone does not establish authorship.

## Review gate

Classify material as original work, external build/runtime components, separately executed reference clients, redistributed third-party source, or externally generated captures/assets. For original contributions, confirm independent authorship, entitlement to license under MIT, contributor notices, and SPDX identifiers where applicable. Identify generators and their input origins for generated material.

For an external component, record its origin, exact version/hash, purpose, license, copyright notices, modifications, build/runtime role, and redistributed bytes. Preserve required terms separately from original MIT work. Inspect the actual installed files and compiled/linker closure; build-tool execution is not the same as bundling its implementation. Keep the [component notices](../../THIRD_PARTY_NOTICES.md) and required GNU source/notice companions accurate.

Raw captures, screenshots, external client artwork, reference repositories, and downloaded tool images stay outside original source/package inputs. They do not acquire MIT provenance by being copied into a directory. A failed authorship or licensing check blocks the affected distribution; it is not resolved by changing the root license or silently incorporating reference code.
