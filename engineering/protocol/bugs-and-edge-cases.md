# Firmware bugs, unexpected behavior, and unsupported edge cases

Original MIT documentation, copyright 2026 Lee Bussy. Created November 15, 2026. This is a living register of firmware compatibility findings discovered during emulator development and firmware review; an entry is not necessarily a defect. No reference implementation, table, test, or asset is incorporated.

## Scope and evidence

The firmware reference is `8f1fa1213cbbfc1f987fada5168d01925e1a2ee8`, normally the Uno/RevC profile selected by the [behavioral contract](behavioral-contract.md). The November 15 rotary review inspected the clean local checkout at that revision, including the Uno, Leonardo, and DIY interrupt branches. It did not run firmware or exercise hardware. Existing emulator/integration evidence is owned by the linked milestone records; a source finding alone is not a passing emulator test or Arduino qualification.

Preserve the Arduino action/reaction, including bugs. This register does not authorize firmware fixes, emulator behavior changes, reference execution, or hardware work. The [contract](../../CONTRACT.md), [firmware findings](firmware-findings.md), and milestone specifications remain authoritative. The F01–F21 rows below retain the existing findings and IDs for discovery; consult their owning specification and fixtures for full preconditions and expectations. New entries here do not silently become fixture coverage or implemented emulator features.

D denotes source-defined behavior. C denotes an exact outcome requiring reference-artifact or hardware characterization; D/C combines known call order or bounded behavior with unresolved outcomes. Source-defined does not mean hardware-verified. U denotes an unsupported UI capability or documented limitation, rather than an undefined result. Keep IDs stable and record future corrections or evidence explicitly.

| --- | --- | --- | --- |
| M01 | D/C | Scalar parsing has a custom integer/fraction/sign grammar and staged fixed-point rounding. Multiple decimal points and minus signs can have unexpected accepted meanings; extreme unit-conversion overflow remains characterization-required. Finite scalar saturation reserves the invalid/disabled sentinels rather than turning sufficiently low numeric values into null. | [Milestone 2 clarifications](milestone-2-details.md). |
| M02 | D | Reload forces the saved mode action; off-mode targets can survive an ordinary no-op mode write but are disabled and stored on reload. Waiting-for-peak state also forces an otherwise unchanged mode action. | [Milestone 2 clarifications](milestone-2-details.md). |
| M03 | D/C | Ordinary negative signed-byte U patch fields are omitted, and a later negative duplicate can cancel an earlier pending update. Calibration instead omits only -1. A pending ROM beginning FF is omitted. Noncanonical booleans and malformed ROMs remain characterization obligations where actually observed/installed; defined configuration validation failures still take precedence. | [Milestone 2 clarifications](milestone-2-details.md). |
| M04 | D/C | Short even-length ROM patches overwrite only their supplied bytes, retaining the pending address suffix. Lowercase hexadecimal conversion is nonstandard; a low-nibble lowercase letter can affect the high nibble. Odd-length/excessive addresses need characterization. First-byte-zero addresses wildcard-match discovery but retain literal addressing for live reads. | [Milestone 2 clarifications](milestone-2-details.md), F20. |
| M05 | D | Discovery leakage is local to each enumeration cursor, not carried from the final probe into the first digital row. Digital enumeration omits v; sensor records can still be read when d includes both w and r. Device attributes serialize through signed-byte values, so pin 200 prints -56. | [Milestone 2 clarifications](milestone-2-details.md), F09. |
| M06 | D | Embedded NUL bytes consume token capacity but truncate callback-visible strings. Diagnostic strings retain unescaped content that can make a record invalid strict JSON. Neither behavior grants the wire protocol strict JSON semantics. | [Milestone 2 clarifications](milestone-2-details.md). |
| M07 | D | Successful sensor reads do not clear the accumulated missed-read counter. Reconnect initialization reseeds histories only after more than 60 missed reads; replacing a sensor retains its wrapper's slope countdown. | [Milestone 3 specification](milestone-3-details.md). |
| M08 | D | Target setters evaluate PID/state synchronously, but do not independently write outputs or emit the regular loop's state-transition report. Blocking serial processing suspends periodic controller evaluations; resumption performs one due evaluation rather than replaying every missed sample. | [Milestone 3 specification](milestone-3-details.md). |
| M09 | D | Door state overrides the LCD state display rather than directly replacing the controller's heating/cooling state. Off mode can display/report idle when missing targets or required sensors override its state. | [Milestone 3 specification](milestone-3-details.md). |
| M10 | U | A host/panel chart can retain Fahrenheit numeric history and subsequently label it Celsius after a unit round trip. ## Rotary encoder, pushbutton, and menu review

The normal UI offers only Mode, Beer setpoint, and Fridge setpoint. Mode order is beer constant, fridge constant, beer profile, and off (`bfpo`). Rotation navigates/previews; presses open/select/confirm. Temperature selection uses tenths of the configured display unit, and the default bounds are 1–30 C. These facts provide context for the edge cases below, not additional implemented emulator UI scope.

All R entries are source-review findings from November 15, 2026. No R entry claims a new automated test, native execution result, physical trace, or completed compatibility gate.

## Adding findings

Append a stable ID, trigger/preconditions, actual response or bounded call order, consequence, classification, pinned evidence, and any available test/trace identity. Distinguish reference firmware behavior, external-client limitations, emulator implementation defects, and unsupported features. Record corrected emulator defects with their fix/evidence rather than treating them as required Arduino quirks. Keep undefined-memory, build-dependent, bus-dependent, and physical timing outcomes unresolved until characterized against an identified artifact; never mark an unresolved case passing or execute native corruption to imitate it.

The existing [cross-milestone review](../development/cross-milestone-review.md) owns resolved emulator/helper defects and their validation; they are not newly open firmware bugs. This document adds no implementation or runtime qualification and authorizes no change to the established behavior-preservation policy.
