# Firmware quirks and compatibility limits

Deterministic firmware quirks are required controller behavior. Undefined-memory, overflow, and hardware-dependent outcomes remain explicit compatibility limits; no safer invented serial response substitutes for them. Original findings use MIT; reference source retains its terms.

D means a deterministic source-defined expectation with original fixture coverage. C means a characterization case whose source bounds/call order are recorded but whose exact runtime result needs hardware/build evidence; no deterministic reply is invented. Hardware characterization is not performed or authorized by this documentation task. A C case cannot be called passing or silently rejected by the emulator; qualify it before claiming the affected compatibility. [Fixture semantics](test-vectors/README.md) distinguish these categories.

## Open evidence requirements

No ambiguity in this register is resolved by correcting firmware behavior. Before claiming exact parity for a C case, retain the exact reference firmware binary/build flags, Arduino type, sensor/bus state, initial EEPROM image/history, exact command bytes/timing, raw response bytes, reset/recovery behavior, and reproducibility. Do not copy those binaries, source, or raw captures into MIT fixture data by default; keep evidence separate and author a minimal interoperability expectation after provenance review. Actual device execution requires a later authorized qualification task.

The original characterization fixtures carry status requires_reference_trace and no invented exact response. They are review/qualification obligations, not disabled passing tests. Ordinary source-defined cases can proceed to independent implementation after user approval, while affected edge claims remain gated on their own evidence. The owner's firmware-first rule remains in force for all later questions.
