## Serial behavior and timing

Expose a raw/no-echo local PTY through the configurable stable path, default `/run/brewpi-emulator/chamber1/serial`. Configure host port explicitly, altport=None, with optional startupDelay=0. The host opens at 57600 baud, normally waits 10 wall seconds, requests n, then s/c/v; it polls l about every five wall seconds and t at its logging interval, default 120 seconds. Read replies within the host's ordinary one-second serial timeout when no firmware-style delay is involved. Do not impose the old 250 ms requirement on hardware-discovery or partial-token waits, which may block in the reference. Opening/closing a PTY has no USB reset circuitry; use R or a process restart for an explicit controller reboot. Sources: [host serial setup](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/BrewPiUtil.py#L376), [startup](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L724), and [polls](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1483).

Commands are case-sensitive bytes. Space, CR, and LF are ignored by dispatch; tab is an invalid command. j, h, d, and U invoke a flat token reader and expect the next byte to be an opening brace, with no added whitespace skipping before it. Within tokens, literal spaces and quote characters are discarded; colon/comma terminate tokens, and a closing brace or read timeout terminates the parse. Key/value buffers hold up to 29 characters. There is no strict JSON validation, escape decoding, nested-object grammar, duplicate-key rejection, or 4 KiB transaction rule. A trailing comma can terminate without an error. Preserve partial application, repeated keys, unquoted scalar input, first-character query/device aliases, and remaining bytes returning to dispatch. A no-data read waits approximately one wall second; do not substitute a simulation-clock timeout. Sources: [dispatch](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L144) and [token reader](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L688).

The value buffer is not cleared before every attempted pair. If a later key reaches the 29-character stop, the value reader is short-circuited and the previous nonempty value can be passed with that new key. The character read while the buffer is already full is consumed/discarded; subsequent bytes return to dispatch. The bounded original fixture with 30 q characters after Kp:7 therefore logs I12 for the 29-character key with value 7, W0, final S/C, then W1 for the remaining closing brace. This case does not require a buffer overrun or an invented malformed-input policy.

Output normally has prefix:payload followed by CRLF. Preserve JSON scalar types and firmware numeric padding/precision; numeric buffers are printed unquoted. Do not assume all output is valid UTF-8: LCD readback carries raw byte B0, decoded by the host as CP437. Ordinary messages are JSON-shaped, but diagnostics can interrupt an open list during nested logging, and strings are not universally JSON-escaped by firmware. Keep this behavior rather than introducing a new strict-output protocol. Fixtures distinguish decoded payload matching from explicit byte matching; the former does not waive the latter. The host already strips embedded D records. Sources: [output](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L440), [LCD export](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/SpiLcd.cpp#L238), and [embedded diagnostic handling](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/expandLogMessage.py#L126).

## Command effects

| Input | Reference action/reaction |
| --- | --- |
| n | N identity response. |
| t | T with full ordinary names and null annotations; omit RoomTemp when ambient is disconnected. No simulator Time field. |
| s/c/v | S/C/V readback. Reads do not persist or clear values. |
| l | Four current LCD shadow rows, each 20 bytes; no independent layout redesign. |
| j{...} | For each nonempty key/value pair, emit I12 before processing it. Apply/persist each recognized successful conversion immediately. An unknown full key additionally emits W0; later pairs continue. Always send final S then C after parsing, including malformed/partial input. Setter annotations may send T before the actual new value is stored. There is no mandatory final T. |
| S | Load volatile default settings, send S, then I14. The mode setter may persist an intermediate settings snapshot; do not replace this with an unconditional final durable reset. |
| C | Load volatile default constants and filter coefficients, repaint stationary display text, send C, then I13. No unconditional store; existing filter histories and V are not cleared. |
| E | Initialize EEPROM-like configuration, defaults, and empty device slots, call controller init, emit I15, then reload settings/devices. No automatic S/C/V/T/d/h acknowledgment set. |
| R | Perform a full controller restart, retaining EEPROM-like saved configuration. No fabricated acknowledgment. Boot/init messages depend on whether saved settings are valid. |
| h{...} | Open h list, enumerate matching OneWire then digital inventory, close list. Raw values and possible nested logging follow reference behavior. |
| d{...} | Open d list, inspect/read/write selected slots in EEPROM order, close list. Special i=-2 camera request still closes as d:[]. |
| U{...} | Parse first-character device keys into signed-byte patch fields, normalize ownership under FORCE_DEVICE_DEFAULTS, validate, uninstall/install, attempt slot store, and return resulting U. Invalid configuration logs specific E then generic E3 and returns old U. Invalid negative/missing index is silently ignored. Slot 16 is a characterization case, not newly rejected. |
| A/a | Set/clear the virtual alarm latch; no response. |
| y/Y/e/Z/F | Unsupported in the selected ordinary debug-0 profile: dispatch W1 for the byte. In particular, y does not consume a following object as a protected unsupported command; its following bytes are also dispatched. |

## Telemetry and display

T fields are BeerTemp, BeerSet, BeerAnn, FridgeTemp, FridgeSet, FridgeAnn, State, and conditional RoomTemp. Temperatures/setpoints are JSON numbers or null, annotations strings or null, and State an integer. There are no compact keys or Time in this profile. A missing room probe causes omission, even if the host retains an old RoomTemp in its merged cache. U does not force T, and j does not force an extra final T. Ordinary brewpiLoop sends T on state changes after updateState and before updateOutputs; direct command-side state changes need not produce the same transition notification. Do not coalesce, move, or sanitize the setter annotations to make them reflect post-mutation state. Sources: [T fields](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L296) and [loop ordering](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Brewpi.cpp#L130).

Required annotation phrases are protocol facts: mode writes produce `Mode set to <value> by web`; fridge-mode target writes produce `Fridge set to <value> by web`; beer writes outside profile mode produce `Beer set to <value> by web`; qualifying profile changes use `by profile`; door changes produce `Fridge door opened` or `Fridge door closed`. A 32-byte annotation buffer truncates to 31 content bytes. Fridge/beer setter annotations occur before setpoint mutation; mode annotation occurs after setMode. Profile annotation appears only when the difference from the old beer target exceeds 100 internal units. These small required wire phrases are not an imported diagnostic prose table. Source: [annotation callbacks](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L762).

L preserves firmware layout, unit bytes, timing suffixes, and room alternation. Line 0 has Mode at column 0 and its value at column 7; lines 1/2 have Beer/Fridge or Room labels, measured and set values at columns 6/12, and the exported B0 byte plus unit at columns 18/19. Room is shown when the ambient probe is connected and bit 3 of ticks.seconds is zero; room display suppresses the chamber setpoint. The host decodes B0 as CP437 and then replaces character 18 with its degree entity; do not change it to a UTF-8 degree glyph or a JSON Unicode escape. The last row reflects the door display override or controller state with the reference's hours/minutes/seconds suffix. Cosmetic changes require explicit future approval, not independent-layout discretion. Sources: [LCD layout](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DisplayLcd.cpp#L72), [LCD exported byte](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/SpiLcd.cpp#L238), and [host LCD handling](https://github.com/brewpi-remix/brewpi-script-rmx/blob/d183fb5319b928f78b4c0eb6f05fe3620610ffff/brewpi.py#L1721).

## Device schemas and queries

Records use i,t,c,b,f,h,d,p and conditional x,a,j,v. i is a slot or -1 for unassigned inventory; t is derived from the assigned function, so an unassigned probe has t=0. h=1 is digital, h=2 OneWire temperature. Functions 0–15 use the reference enum/type/target mapping: 1 door, 2 heater, 3 cooler, 4 light, 5 chamber probe, 6 ambient, 7 fan, 9 primary beer probe; reserved/secondary functions may pass storage validation without any live target. Do not newly reject them as unsupported solely because the panel hides them. a is eight bytes printed as 16 uppercase hex characters. j is calibration in current temperature-difference units. The h=1 invert flag x and deactivation d are serialized numeric 0/1. Source: [record types](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.h#L58) and [formatting](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L573).

| f | Output t | Stored meaning and live target in the selected build |
| --- | --- | --- |
| 0 | 0 | Clear the slot completely; no live target. |
| 1 | 2 | Door input. |
| 2, 3, 4, 7 | 3 | Chamber heater, cooler, light, and fan, respectively. |
| 5, 6 | 1 | Chamber and ambient probe, respectively. |
| 8 | 0 | Reserved chamber record, no live target; h=0 can pass type validation. |
| 9 | 1 | Primary beer probe. |
| 10 | 1 | Secondary beer probe record; no live target. |
| 11, 12 | 3 | Beer heater/cooler records; no live target. |
| 13, 14, 15 | 0 | SG/reserved beer records, no live target; h=0 can pass type validation. |

Source: [live target mapping](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L155). Output-only type is derived from f even if no live target is available; do not invent a successful sensor/actuator read for those records. A d read of a no-target record has no v because the source returns before producing a value.

h defaults are h=-1,p=-1,v=0,u=0,f=0. Keys are matched by first character and unknown keys ignored; numeric selectors are narrowed to signed bytes. u is truthy for any nonzero value, including -1. f selects assignable device type rather than equality to an installed function. Enumerate OneWire probes in the reference's zero-branch-first, least-significant-bit-first search order, then actuator pins in reference order 2,5,6,19. For the selected synthetic ROMs this is chamber, beer, room, not numeric/lexicographic ROM sorting. h=0/3 has no supported inventory in this build; do not invent a query error. Disconnected hardware disappears from discovery but installed slots remain. h v readings are uncalibrated; installed d r readings are calibrated, unfiltered, while T uses fast-filtered beer/chamber readings. Digital h output omits v even with a values request; h/d temperature values use three decimals. The OneWire and digital enumeration cursors are separate, and each is reused within its own group; a matched installed record can leak its f/b/d/etc. into a later unassigned record in the same group, but not from OneWire into digital enumeration. Preserve that quirk as finding F09. Sources: [enumeration](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L740) and [defaults](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L886).

d defaults are signed-byte i=-1,r=-1,w=-1,e=0. All-slot output omits f=0 unless e is nonzero; a specific in-range i returns that slot even if empty. r must equal 1 to return values. Any nonnegative w writes an actuator as logical (w != 0), takes precedence over r for that actuator, and omits its v; sensor types still honor r=1 and are not written. i=-2 writes cameraLight and returns an empty d list. Deactivated slots remain installed, but their live target is the shared default object; reads/writes follow that object, not a newly invented always-null/zero rule. Out-of-range selector indices normally yield an empty d list, not an error. Sources: [slot selection](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L658) and [read/write handling](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L917).

U fields match first-character aliases, ignore unknown/output-only t/v, and accept a reserved n byte without enabling DS2413. Ordinary signed-byte patch fields apply only when nonnegative, so every negative value is omitted on application; calibration separately applies any signed byte except -1. FORCE_DEVICE_DEFAULTS sets c=1 and b=1 for supplied f in 9–15, otherwise b=0, before applying the patch; it ignores even out-of-range supplied ownership values. Therefore a patch omitting f can invalidate an existing beer slot. f=0 clears the whole record. Slot bound checking admits 16 although EEPROM access does not: this is a characterization hazard, not an opportunity to add E3. No active uniqueness check rejects duplicate ROMs/pins/functions; duplicate slots can remain while live ownership changes. Probe validation requires an existing OneWire bus, not a discovered known CRC-valid ROM; zero-address first-on-bus is allowed. Discovery treats zero addresses as wildcard matches, but the live OneWire path still selects the literal zero ROM; do not silently implement the header's promised first-sensor resolution where the active source does not. See F20. Sources: [patch semantics](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L394), [actual validation](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L480), and [address meaning](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.h#L170).

EEPROM reload calls device validation directly, without U's ownership normalization. Its accepted ownership bounds are inclusive chamber 0–4 and beer 0–6, even though the live target mapper only supports chamber/beer up to 1. Out-of-range stored values can emit E4/E5 at reboot; the reload then clears/stores the invalid slot without U's extra generic E3 or a U reply. Do not treat E4/E5 as unreachable for the selected profile or impose U's normalization on saved records. Sources: [reload validation](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/EepromManager.cpp#L124) and [format bounds](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/EepromFormat.h#L47).

For stored-record ownership, a beer function requires nonzero beer, a chamber function requires nonzero chamber, and function 0 requires both zero; the validator does not additionally require every beer function's chamber to equal 1 or every chamber function's beer to equal 0. The live-target mapper separately returns no target for chamber>1 or beer>1. Thus a stored c=4,b=6,f=9 record with compatible probe hardware can validate and remain stored while supplying no live input or d reading. Preserve this accepted stored/live distinction; do not apply the panel's narrower ownership model as a new validator.

Calibration is stored as signed 1/16 C with byte narrowing, not independently range-validated or rounded to nearest. A candidate whose stored calibration byte is -1 is treated as absent, so a -0.0625 C adjustment cannot be applied normally. Preserve the collision, including its rounded decimal-token behavior. Digital pins are not validated against the discovered actuator list; unknown valid numeric pins can be accepted. Their electrical/plant effect is a virtual hardware mapping/characterization concern, not a fabricated controller validation error. ROM lengths beyond eight bytes and ambiguous memory-dependent cases are registered as trace-required; do not manufacture stable output. The [findings register](firmware-findings.md) supplies required deterministic and characterization vectors.

## Controller and persistence characteristics

Use the source's C/AVR widths, fixed-point observable values, callback order, timer boundaries, and live filter-routing behavior. This is independent implementation of matching actions, not permission to port code. State numbers are 0 idle, 1 off, 2 LCD-only door override, 3 heating, 4 cooling, 5 wait-cool, 6 wait-heat, 7 peak wait, 8 minimum-cool hold, 9 minimum-heat hold. Off mode may report idle due to disabled-target precedence. Test mode skips output updates and camera auto-off processing, even while its state calculation continues. Command setters can change state without updating physical outputs until the next ordinary loop tick. Missing-sensor shutdown is not advanced ahead of that loop merely to be safer. Positive Kd and a positive reported beer slope produce an additive positive d contribution in the pinned source; do not insert the conventional negative sign. Source: [PID/state/output actions](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L160).

The reference integral counter advances on beer-mode PID evaluations, including command-triggered evaluations, with its first periodic branch on the 61st qualifying evaluation, not a redesigned exact 60-second timer. Peak diagnostics begin as zero-initialized raw values (displaying 48 C), and S/C/E do not generally clear V. C changes coefficients without reseeding histories; beer filter j writes have the documented misrouting. Minimum-on release uses strict greater-than at 180 seconds, so exactly 180 remains a hold when its stop criterion is true. Preserve 16-bit seconds and AVR-like wrap observables in controller timers, separate from a wider plant clock. Every such fact is a conformance requirement, not an assertion that a matching native implementation already exists. Sources: [control evaluation](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L160), [minimum on](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L370), and [filter callback](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L839).

E is not a full MCU reboot. Its controller init sets state to idle and mode off, clears the camera request and peak-detection flags, and assigns last-heat/last-cool timestamps to zero. It does not explicitly clear V, last-idle/wait/door state, the alarm latch, or the PID evaluation counter; called sensor/settings actions can have their own effects. S/C also do not generally clear those histories. R restarts the MCU-like volatile state and its static initialization, so it differs from E. Likewise, issuing mode o while already o and not in a waiting state is not a forced reset; setMode can be a no-op, leaving otherwise written off-mode target values intact. Preserve these distinctions instead of treating every reset/mode command as a universal cleanup. An invalid saved controller-format version follows safe-mode behavior rather than silently resetting identifiers; host-filesystem corruption/IO failure is an emulator-environment failure, not an invented Arduino diagnostic ID. Keep emulator instance IDs/virtual ROM configuration separate from the controller's EEPROM-like contents. This preserves stable synthetic hardware across E/R while modeling saved-setting quirks faithfully.

## Thermal environment and completion boundary

The virtual thermal plant is independently modeled external hardware, not a replacement control policy. Its baseline is specified in defaults: five US gallons, physical probe locations, fixed load wiring, three separate temperatures, fermentation heat, capacities, and lag. Controller outputs act through pin polarity; assigning a different function does not move a probe or change a refrigerator into a heater. Acceleration advances controller and plant time together, while serial token waits and the host's profiles/chart timestamps retain wall time. A paused plant does not justify suppressing command-triggered controller actions. Explicit checkpoint resume restores coherent controller/plant/history/timer/random state without adding downtime; default process restart resets the external plant to scenario initial conditions while loading only firmware-saved settings.
