# Controller and physical model

Original MIT specification of controller, filter, clock, and physical-model behavior. Pinned source links record interoperability facts; reference implementation is not incorporated.

## Scheduling, sensors, and filters

A normal controller evaluation orders temperature acquisition, peak detection/adaptation, PID, state evaluation, transition `T`, output writes, then LCD/UI update. A target callback evaluates PID and state synchronously but does not independently write outputs or emit the ordinary loop transition `T`. Mode-only callbacks do not evaluate PID. The normal UI has no startup-page delay; the separately modeled display initialization and conditional probe conversion waits still precede normal dispatch. Serial token blocking suspends controller evaluations while physical time and the external equipment continue; after blocking, execute one due evaluation, not a burst of missed sensor/controller samples. Sources: [ordinary loop](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Brewpi.cpp#L102), [target callbacks](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L705), and [UI](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/UI.cpp#L40).

The selected filter is three cascaded second-order sections, each with coefficient `b` and byte-valued `a=(2b+4) mod 256`. Its real-valued transfer function has numerator `2^-a` times `[1,2,1]` and denominator `[1,-2+2^-b,1-2^-b+2^(2-a)]`. Interoperable integer evaluation is more specific than this transfer function: retain each input/output product's arithmetic shift separately, extrapolate the last two outputs, and apply 32-bit fixed-point storage with 16 fractional bits beyond ordinary temperature raw units. Rounding each coefficient product separately is required; floating-point evaluation of the combined transfer function is not an equivalent oracle. Seed every section's two input and two output delays with the initial calibrated temperature; seed slope sections with zero. Peak detection compares the last three final-section outputs: a strict downward turn after a nondecreasing step is a positive peak, and the inverse is a negative peak. Sources: [filter coefficient facts](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/FilterFixed.h#L42), [integer filtering](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/FilterFixed.cpp#L42), and [cascade selection](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/FilterCascaded.h#L37).

The two retained Uno artifacts define the variable shifts for every coefficient byte, including values outside ordinary stable filter settings. Every count is narrowed to a byte: 0 and 129..255 leave the operand unchanged, 1..31 shift arithmetically, and 32..128 yield its sign-filled word. This applies to `b`, `a`, `a-1`, and `a-2` separately; subtraction of the count wraps as a byte. The real-valued transfer function above describes ordinary coefficients, not these emitted-loop discontinuities. [Artifact comparisons](firmware-findings.md#artifact-arithmetic-and-bounded-input-behavior) establish this exact-build behavior; it is not a portable signed-shift guarantee.

Beer/chamber sampling updates fast and slow histories once per controller evaluation. The unsigned slope countdown starts at 255, captures a slow-output baseline at 4, and updates slope at 0 before resetting to 3. Multiply the precise slow-output difference by 1200, clipping differences whose raw upper word exceeds +/-27 before multiplication. Successful reads do not reset the missed-read counter; it saturates at 255, and reconnect initialization reseeds histories only when missed reads exceed 60. Replacing a sensor reseeds connected histories but retains the wrapper's slope countdown. Preserve the previously documented incorrect live beer filter write routing; `C` and reload apply the correct named coefficients without an extra history reset. Source: [sensor history](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempSensor.cpp#L40).

## PID and state actions

Beer modes `b/p` derive error from beer target minus slow beer temperature, and slope from the filtered hourly beer slope. Gains multiply raw error/integral/slope, shift by 9, and saturate to raw -32766..32767. Add `p/i/d` positively to the beer target, saturate, then constrain between `max(tempSetMin, beerTarget-pidMax)` and `min(tempSetMax, beerTarget+pidMax)`, preserving the source's conditional boundary construction. Fridge mode `f` disables the beer target. An invalid/disabled beer target makes the derived fridge target disabled without clearing stale `V`.

Integral work first runs on qualifying PID evaluation 61, then every 61 evaluations. Non-idle evaluations contribute zero at that branch. Below the strict `iMaxErr` threshold, matching error/accumulator signs integrate only when the previous fridge target is inside temperature/PID limits and the measured fridge is within 2 C of the previous target in the requested direction; opposite signs double the update. At or outside `iMaxErr`, decay the accumulator by its arithmetic-shifted one-eighth value. The accumulator stores the wrapped 32-bit result; the branch update narrows to a signed temperature word before addition. The selected artifacts retain -32768 after signed-word magnitude, so that boundary enters the below-threshold branch; see [artifact arithmetic](firmware-findings.md#artifact-arithmetic-and-bounded-input-behavior). Neither mode changes nor `E` clear this evaluation counter. Source: [PID facts](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L160).

State numbers and thresholds are those in the reviewed contract. Door changes annotate before state changes and override only the LCD display state, not the heating/cooling state. Mode off selects state 1, then invalid fridge target or missing required sensors overrides it to idle 0. Idle/off/wait states set last-idle to now; a forced idle condition retains the previous wait duration. Otherwise, wait duration is the maximum still-required switch/off delay. Cooling demand is strictly above target+`idleRangeH`; heating is strictly below target+`idleRangeL`. Beer modes additionally suppress cooling below `beerTarget`+16 raw units and heating above `beerTarget`-16. Only a live configured actuator (or configured light when `lah` is `true`) admits its demand. An already active state marks peak detection pending, stamps its active timestamp, and predicts overshoot as `estimator*min(activeSeconds,timeLimit)/3600` added to fast fridge temperature, with the cooling sign negative. A stop condition holds state 8/9 until since-idle is strictly greater than 180. Unfinished peak detection can replace a new active state with state 7 even at a zero remaining wait duration. Sources: [state decisions](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L248) and [estimated peaks](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L422).

Peak adaptation uses slow-filter turning points after the corresponding output stops. Heat overshoot error above `heatTargetH` increases the estimator; below `heatTargetL` decreases it. Cooling reverses those comparisons. Increase uses factor `614+clip(abs(error)>>5,0,154)`, with a minimum resulting estimate of raw 25; decrease uses factor `426-clip(abs(error)>>5,0,85)`. Multiplication uses fixed-point arithmetic and persists settings. At strict timeout >900/1800 seconds, a sufficiently drifting fast temperature can replace the missing peak for logging, but the error was already calculated from the missing-peak sentinel and must not be corrected. `I17`/`I18`/`I19`/`I20` carry the documented formatted strings. The selected artifacts retain signed-word magnitude at -32768, giving a clamped magnitude term of zero and factors 614/426; explicit long-word products wrap before shifting. This is [artifact-scoped arithmetic evidence](firmware-findings.md#artifact-arithmetic-and-bounded-input-behavior), not qualification of every extreme history. Source: [adaptation facts](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L449).

Output updates return immediately in test mode, including skipping camera timeout. Otherwise camera requests expire at elapsed >=600 seconds; cooler follows states 4/8, heater follows 3/9, light follows door or camera or `lah`-and-heating, and fan follows either active direction. Writes target configured pin polarity, or the shared fallback actuator if unconfigured/deactivated. Physical load locations do not change when logical functions change. Sources: [outputs](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L435) and [camera timing](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/ActuatorAutoOff.cpp#L33).

The selected artifacts wrap the precise slow-channel slope difference to 32 bits before applying its magnitude bound. Widening that difference before the clamp can reverse the selected sign at extreme histories; [artifact arithmetic](firmware-findings.md#artifact-arithmetic-and-bounded-input-behavior) and original core regressions preserve the emitted order.

## LCD, clock, and independent external plant

LCD is a retained four-by-twenty byte shadow, not a new JSON view of current state. Loop updates state text/times, measured/set temperatures, and mode. Room appears when ambient is connected and bit 3 of controller seconds is zero. Invalid temperatures occupy six cells; ordinary valid temperatures are aligned to the right to five cells. Mode values are `Fridge Const.`, `Beer Const.`, `Beer Profile`, `Off`, `** Testing **`, or `Invalid mode`; state phrases and right-aligned `h`/`mm`/`ss` time suffixes follow the reference's small required wire literals. Stationary repaint on `tempFormat`/`C` updates units without inventing a full UI refresh. Raw byte `B0` remains the exported degree cell. Source: [LCD actions/layout](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DisplayLcd.cpp#L72).

Controller milliseconds wrap at 32 bits; seconds are `millis/1000` narrowed to 16 bits, and duration comparisons subtract modulo 65536. A wider external clock tracks plant age. `R` resets the controller clock, histories, latches, and volatile globals while preserving external plant state/age and saved controller configuration. `E` resets only the reviewed subset. Process restart begins a fresh configured external plant unless explicit checkpoint resume is selected. Source: [hardware ticks](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TicksWiring.cpp#L35).

The independent physical model uses `Cb*dTb/dt=Kbc*(Tc-Tb)+fermentation` and `Cc*dTc/dt=Kbc*(Tb-Tc)+Kcr*(Tr-Tc)+heater-cooler+auxiliary`. Capacities and default inputs are the original reviewed scenario, not firmware simulator source. Integrate with a fixed 100 ms midpoint step, with conservative shared exchange terms; output electrical latches, rather than assigned function labels, determine load watts. Optional sinusoidal room conditions, sensor lag/quantization, deterministic bounded noise, door conductance, and the reviewed piecewise-linear fermentation profile are explicit external scenario inputs. Acceleration only changes wall pacing; it does not change that step or controller thresholds. Retain fractional elapsed simulation milliseconds and every controller/filter/random/plant/LCD state needed for checkpoint resume, without adding stopped wall time. These are original external model and scheduling choices, not replacement Arduino control policy.

The normal profile reinitializes the LCD every 3600 controller seconds, using a 32-bit last-reset timestamp compared with narrowed controller seconds. Reinitialization clears the shadow, resets room-alternation flags, and forces state text repaint; ordinary UI updates then restore temperatures/mode. This timer is independent of controller histories and is retained in checkpoints. Source: [reset interval](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Config.h#L111), [display reset state](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DisplayLcd.cpp#L58), and [loop reset ordering](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Brewpi.cpp#L110).

The independent filter arithmetic test expands the `b=0` cascade analytically as `(1+z^-1)^6` / `[4096*(1-z^-1/2)^6]`. For an impulse of `2^25` precise units, its first nine outputs are integral and can be calculated by binomial coefficients without running either implementation. These original mathematical oracle values test more than coefficient metadata; conventional DSP mathematics is permitted by the independent-authorship contract.

External scenario capacities are sums of nonnegative physical components; validate each declared volume/density/specific-heat/capacity component before combining them, and require positive resulting beer/chamber capacities. A positive derived sum must not conceal a negative component. The native integral-branch count is checkpoint instrumentation, not an Arduino word; restore its nonnegative integer value throughout the exact JSON integer range without imposing an unrelated 32-bit controller width.

## Sensor recovery and initialization

A backend that has noticed loss cannot perform an ordinary filter sample in its recovery evaluation. That evaluation increments the failed-read count, attempts reconnection, and seeds fast/slow histories and zero slope only when the count exceeds 60; initialization retains the slope countdown. Successful ordinary readings do not clear a smaller accumulated failure count. Subsequent ordinary evaluations resume sampling and slope cadence. Beer is required in beer modes, chamber is required for control in all ordinary modes, and ambient loss changes telemetry without becoming a required control input.

A known probe reset indication selects a 750-millisecond conversion wait after connection setup. The existing 100-millisecond integration grid services completion after 800 milliseconds; sequential initializations each retain their own wait. Controller/plant clocks and physical loads continue while dispatch and the suspended controller/assignment/discovery continuation wait. Setup clears the reset indication before conversion, so a second reset or DATA loss during the wait can fail initialization instead of producing an invented successful sample. Warm DATA-only recovery does not enter this branch. Discovery preserves its partial reply and resumes at the waiting row; a checkpoint continuation assumes the client retains any already delivered prefix.

Startup and full controller restart include the profile's modeled mandatory display waits, then installed-device initialization in slot order, then the first ordinary evaluation. Native fixture construction can select the post-display boundary explicitly to isolate control assertions from startup timing. The executable always includes startup initialization; paused startup completes at 1x before runtime pacing stops. These are source-defined minimum-delay semantics, not an exact MCU bootloader, UART, OneWire-wire, or conversion-freshness qualification. See the [findings and remaining limits](firmware-findings.md#sensor-recovery-and-initialization).

## Menu execution and serial buffering

The selected Uno builds share the [menu selection paths](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Menu.cpp#L50) and [logical encoder change detection](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/RotaryEncoderBase.cpp#L166). Top-level items are mode, beer, and fridge; modes cycle `b/f/p/o`. Encoder ranges wrap at rounded endpoints without clamping their starting value. Push counts as a change, so unrotated temperature confirmation passes through display tenths rather than retaining the original word's extra precision. Temperature conversion uses the selected C/F format, with defined rounding and internal saturation; half-step electrical decoding does not double an idealized logical event. An invalid mode's lookup can index outside the reference array, and remains a local fidelity limit rather than an invented corrected choice.

Mode rotation invokes the mode setter immediately, with its state and persistence effects. A mode timeout invokes that setter for the previous mode; it does not restore targets disabled while off was selected. Entering a temperature editor directly invokes its constant-mode setter. Temperature rotation changes the candidate display; confirmation invokes the target callback and annotation, while timeout does not store the candidate. The [target callbacks](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/TempControl.cpp#L705) retain their peak reset, PID/state evaluation, and store order. `R` retains only the resulting saved configuration, not the menu; `E` retains its separately specified reset behavior.

The [UI entry point](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/UI.cpp#L76) runs before the periodic display reset, ordinary controller evaluation, and serial receive in the [main loop](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/Brewpi.cpp#L104). Menu waits call no ordinary sensor, PID, state, or output update; mode and target callbacks can still mutate state as described above. Plant time advances with the firmware clock, outputs stay latched, and door contact changes are sensed at the next allowed evaluation. Exit resumes the display-reset check and one due evaluation before queued serial dispatch, without catch-up sampling. After UI initialization, logical encoder position/change history and the push latch survive other blocked operations. Startup display initialization precedes encoder initialization; local encoder events are unavailable during that phase. The ten-second menu timeout compares wrapped 16-bit firmware seconds, and the native 100-millisecond integration grid bounds completion precision. Wall time remains relevant to the separate serial token deadline and presentation dimming, not to menu timeout. At zero speed local actions remain available, but menu time does not advance.

The native transport reads batches up to 1,024 bytes into a separate bounded virtual-wire admission queue, then serializes incoming good-byte frames at the nominal matched-peer UART rate. Each completed RX frame enters the artifact-qualified oldest-63/newest-drop software queue. Menu, display, sensor, and full-TX writer waits can therefore overflow RX; OS read batch size alone does not determine loss. Arrivals completing during startup display initialization are discarded before application RX enable; periodic display resets leave RX enabled. Accepted decoded bytes retain order and ordinary parser behavior, including partial-token application after a dropped delimiter. RX loss can also reach an existing odd/excessive-ROM or memory-sensitive fidelity limit; it does not trigger automatic command repair or an invented Arduino reply.

The executable enables the [bounded nominal TX model](firmware-findings.md#bounded-uart-transmit-scheduling): 63 software positions plus the data buffer and shifting frame, with one completed 8N1 frame every 170 microseconds under the nominal 16 MHz Uno clock and the retained divider. Output reaches the native transport only after frame completion. A full transmitter blocks the actual synchronous writer, preserving its position relative to mutations, stores, and output changes; it does not run the action ahead and delay only its reply. During the wait RX continues, clocks and the plant advance, and ordinary controller/menu work remains suspended. The receive loop completes available decoded serial work before returning to the next ordinary controller evaluation, without synthesizing missed catch-up evaluations. Pending background TX alone does not suspend controller work.

Streaming also preserves observable action boundaries inside replies. The pinned [d/h dispatch](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L261) opens the list before parsing its query. A [device-list iteration](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/DeviceManager.cpp#L976) updates/reads one slot and prints it before moving to the next; later pin writes cannot run ahead of a blocked earlier row. Telemetry emits its cached beer/chamber fields before the [raw ambient read](https://github.com/brewpi-remix/brewpi-firmware-rmx/blob/8f1fa1213cbbfc1f987fada5168d01925e1a2ee8/src/PiLink.cpp#L355), preserving loss and nested-diagnostic placement if availability changes during the preceding write. These are logical hardware-access boundaries, not per-instruction formatter timing.

Elapsed peripheral credit is shared across nested write waits. A blocked writer resumes at the first completed TX frame that frees space before later elapsed credit is spent; RX and TX events share that chronology, with decoded input queued before ordinary work at a tied boundary. The runtime advances controller/plant time with the same elapsed credit and preserves fractional milliseconds without charging a nested wait twice. This is nominal event scheduling with the existing 100-millisecond controller/plant integration grid, not instruction-cycle simulation.

Direct core tests can inject decoded byte batches at one logical arrival boundary. In those tests the unread suffix precedes later decoded arrivals and competes for RX capacity when the consumer blocks. The executable instead supplies incoming bytes through the nominal virtual wire, avoiding a fictitious instantaneous burst from an OS batch. New native reads wait until earlier elapsed peripheral credit has been processed, so bytes observed later are not injected into the past. The 64 KiB native input admission queue and completed-output backpressure threshold are host transport boundaries, distinct from either artifact software ring. Native backpressure preserves admitted/completed bytes; USB bridge loss is not invented.

Peripheral time follows positive controller pacing; at zero speed RX/TX continue at 1x while runtime controller/plant clocks remain paused. Serial token deadlines remain wall-clock deadlines and refresh after decoded input or blocking. Checkpoints require drained TX, completed incoming wire frames, no suspended/faulted writer, and no unrepresented decoded input; they do not serialize a C++ call stack or silently omit bytes or frame phase. Incompatible older RX queues remain rejected transactionally. Existing idle snapshots remain usable. Administrative shutdown drains admitted wire frames and accepted TX without executing more commands, with a bounded local failure if it cannot finish; interruption of an active writer cannot produce a successful checkpoint. The existing R boundary drains preceding accepted TX before reset, consistent with the source watchdog wait allowing its short tail to finish; exact watchdog/bootloader timing remains outside the model.

The incoming sender is nominally matched to the device's derived UART rate. This is an explicit synthetic arrival schedule, not a measurement of an external USB bridge's clock. The model does not reconstruct physical input timestamps from PTY batches or simulate instruction cycles, ISR latency, parity/framing flags, hardware RX overrun, USB/DTR reset, bootloader buffering, oscillator tolerance, or electrical edges. Native host scheduling can coalesce completed frames; it does not establish microsecond wall-clock delivery or physical throughput qualification.

Menu and logical encoder checkpoint metadata is optional for legacy idle snapshots. New snapshots preserve active phase, candidates, timeout/blink origin, saved display alternation, encoder range/comparison/push state, and queued bytes; restoration validates them transactionally and performs no setter, annotation, or store. Emulator-only presentation cleanup preserves this continuation. Explicit local cancellation closes the menu while retaining already performed mutations; it is not an Arduino button gesture or a timeout rollback.
