## Required controls and interaction

- Retain the green four-row, twenty-column LCD, degree symbol, firmware text/layout, display history, and room alternation outside menu editing. GUI controls must not alter cell geometry.
- Provide a usable original rotary control with center pushbutton, clearly labeled counterclockwise/clockwise alternatives, visible keyboard focus, Left/Right rotation, and Enter/Space pushbutton activation in the appropriate focused control. Prevent widget defaults and application bindings from processing the same activation twice. Door-button keyboard activation must operate the door, not also press the encoder. One deliberate press is one action; no long-press, double-click action, contact-bounce simulation, or held-key/button repeated confirmation.
- Preserve top-level Mode, Beer, Fridge ordering; mode order `b`, `f`, `p`, `o`; clockwise increment, counterclockwise decrement; and endpoint wrapping, including temperature endpoints. GUI/CLI events represent one decoded logical step, not raw pin edges. Preserve full/half-step firmware interpretation if exposing/testing an electrical input layer; never accidentally double a logical command because hs is enabled, and do not add GPIO/hardware scope.
- Provide GUI door control labeled with its next action, Open door or Close door, and authoritative modeled-door feedback. CLI commands set explicit open/closed state; repeating the same request is an acknowledged no-op. Use the existing physical plant door input, not a forced controller state, alarm, relay write, or auto-assigned sensor. Existing door pin assignment, inversion, sensing, annotation, light, thermal conductance, reset, and checkpoint rules determine the downstream result. A paused plant may accept input state without inventing a scheduled controller evaluation.
- Terminal mode retains the LCD and adds exactly one reusable command/status line below it. Commands are `cw`, `ccw`, `press`, `door open`, `door close`, and `help`. Enter submits the textual command; only `press` emulates the physical pushbutton. Do not add a controller quit/reset command or extra settings menu.
- On command submission, erase/rewrite that same line with a brief acknowledgment, then erase/rewrite the prompt. Errors and compact help also occupy that line, never scrolling or adding a newline per command. New typing dismisses the acknowledgment immediately and is retained. Use a nonblocking wall-clock deadline for acknowledgment; document its chosen brief duration. Distinguish accepted local action from confirmed controller-setting commit in feedback.
- Bound terminal input and display width; prevent wrapping, control-sequence injection, and output corruption on invalid, pasted, or long input. Preserve ordered complete commands within bounded capacity; explicitly reject overflow, never truncate it into another valid command. After an overlong line, discard through its submission terminator before accepting a fresh command, so a valid-looking suffix cannot execute. Support normal basic editing, CR/LF submission without duplicate execution, and Ctrl-C shutdown. Use a private foreground controlling terminal, not redirected stdin/stdout or the controller PTY. Do not mutate inherited stream flags.
- Interactive terminal mode requires cursor rewriting and enough geometry for panel, prompt, and wrap protection. Suspend interactive input/output when too small or backgrounded, discard the draft on loss of usable control ownership, and resume coherently without replaying buffered keystrokes as hidden actions. Unsupported terminals get an explanation and no scrolling command-interface imitation. A safe existing read-only fallback may remain if clearly identified. GUI remains usable when no terminal exists; --lcd off stays headless without Python or interactive-terminal side effects.
- Restore owned terminal attributes on clean/handled shutdown, failure/fallback after acquisition, and before job-control suspension; reacquire/revalidate on foreground resume. Preserve signal/shutdown semantics. Do not promise SIGKILL cleanup or consume/flush unrelated shell input.

## Staged menu and deterministic exceptions

Implement one C++-owned, nonblocking menu state machine: controller screen, setting selection, mode selection, beer editor, and fridge editor. Python sends physical-action intents and renders authoritative feedback; it must not own controller settings, confirmation rules, or a duplicate menu.

Keep drafts separate from live state. Browsing, menu entry, and timeout must not invoke setters, reset waits/peak flags, write storage, disable targets, or emit committed-setting annotations. Legitimate background controller changes continue; compare tests against an equivalent no-menu run rather than expecting time/state to freeze. Idle rotation wakes the display without changing settings. Opening press wakes and opens the menu.

Selecting Beer/Fridge stages the matching constant mode and target. Selecting a constant mode opens its target editor. The final temperature press commits the intended mode followed by its target, without interleaving another event/controller evaluation between those two parts; preserve the firmware setter order, normal stores, and subsequent deferred output updates. This is intentional-operation grouping, not a new promise of single-write or crash-atomic persistence. Confirming Profile/Off in the mode editor is final; only an actual committed Off invokes its normal target disabling. Do not call serial j internally: it would introduce web diagnostics/annotations and conversion side effects.

For finite in-range targets, confirmation without rotation preserves the exact original internal value, including sub-tenth precision. Track whether rotation occurred; turning away and back uses the selected firmware-compatible tenths conversion, not the untouched-original rule. Selecting the same value does not authorize skipping other required confirmed setter effects. Invalid/disabled targets start at 20 C converted to current units and bounded to the valid interval. Explicit confirmation can replace the sentinel with that selection.

Local confirmation cannot save an out-of-range target. Start an out-of-range selection at the nearest endpoint and enforce bounds again on confirmation; this approved exception takes precedence over unchanged-target preservation. Reject editing when bounds are invalid, disabled, or reversed, with local feedback and no mutation. Do comparisons in internal units. For rotated selection, derive representable tenth-unit endpoints inside the exact interval, not rounded values outside it; an exact endpoint remains usable for bounding. If an interval has no representable tenth, retain exact valid/bounded values and give deterministic no-increment feedback rather than selecting outside it. Test both units and narrow/non-tenth bounds.

Bounds changes and range reconciliation must remain local UI policy: invalidate affected drafts and reopen from current bounds with the nearest valid selection. Do not globally clamp or persist a target merely because serial changed bounds, do not rewrite arbitrary serial targets, and do not change serial converters or acknowledgments. The actual local target write occurs on explicit confirmation. This reconciles the approved nearest-boundary rule with no browsing side effects and unchanged serial behavior. If a future owner instruction explicitly requires automatic live clamping on serial bounds changes, request a narrow decision before changing that boundary.

Cancel drafts on external changes to their editable dependencies: mode, relevant independently written target, units, or bounds. Observe actual external mutations, including intermediate changes in one serial transaction that later restore a value; do not rely only on final-value comparison. Do not invalidate a beer draft for routine PID-derived fridge target updates, sensor refreshes, or normal state/timer changes. Process accepted serial mutations before a local confirmation in the same event-loop turn; validate the draft revision again before commit. Preserve serial grammar, command order, token blocking, and backpressure. Reject local setting commits while a partial serial mutation is pending or required output/storage capacity is unavailable; give local feedback, do not inject frames inside another serial reply or build an unbounded deferred-action queue.

An existing mode outside bfpo gets a local invalid indication, no out-of-bounds indexing, and no silent default write. Require an actual valid choice before enabling confirmation. Only local controls restrict modes; saved-state and serial mode behavior remain compatible.

Use a nominal ten-wall-second inactivity timeout and wall-clock blinking. Preserve the approximate firmware blink cadence, not its CPU-blocking loops. Rotation/press refreshes menu inactivity; keep command typing, help, door actions, and rendering separate from encoder-menu activity. Deliberate local interaction can refresh display brightness without committing or indefinitely extending an abandoned menu. Process an event at or after the inactivity deadline only after expiring the old draft, so a late press cannot commit expired data. Define/test ordering at exact deadline boundaries.

During menus continue thermal integration, temperature sampling, PID/state/output evaluation, serial reception, and GUI heartbeats under their existing normal scheduling rules. Preserve existing intentional simulation pause, serial-parser blocking, and output-backpressure behavior; do not implement a general scheduler rewrite. Refresh measured readings/state behind editing fields and temporarily suppress room alternation. On exit restore the current live view, not entry-time state. Keep raw serial LCD degree bytes and Unicode conversion boundaries intact; preview mode/targets must never leak into S/T/controller state as committed values. Specify/test how LCD overlays affect L versus local presentation consistently with the approved menu exceptions and existing retained-shadow contract; avoid a second telemetry-derived LCD renderer.

Preserve appropriate confirmed setter effects, firmware menu annotation wording/channels and 31-byte content limit; emit after applying the confirmed operation. Local annotations must not use the web interface's pre-mutation annotation path. Storage failures retain existing application error handling; never display a false successful commit or attempt a blanket rollback of background state.

## Dimming, lifecycle, and bounded transport

Use one wall-clock display-activity model in GUI and terminal. Default inactivity follows the reference's 60-second backlight period and strict greater-than threshold, expressed in wall time. Dim LCD text only; keep terminal prompt and controls readable. Every deliberate turn/press wakes and acts normally; command typing and door interaction also wake the local presentation. Add an explicit documented keep-backlight-on option available in both modes. Decide its ordinary CLI spelling without changing existing option meanings. Dimming/brightness must not change raw LCD characters, serial L bytes, controller timers, or EEPROM-like state.

Cancel drafts on controller R/E reset paths, other external relevant state resets, GUI failure/ownership loss, deliberate shutdown, and checkpoint resume. Discard queued actions from the lost session. Failure falls back; deliberate close stops the emulator as specified above. Treat menu drafts, input queues, acknowledgment text, cursor state, activity timers, and GUI state as transient interface state, not saved controller settings. Preserve plant door state under its existing checkpoint/reset contract. Ensure checkpoints do not resurrect a menu overlay or break retained LCD-history guarantees; keep committed state exact. If a compatible checkpoint schema evolution is necessary, document/backward-test it rather than dropping existing validation or forcing an unsolicited repaint of ordinary no-menu checkpoints.

Use the inherited private IPC only, with versioned strict schemas, bounded messages and per-turn work, ordered action IDs/session identity, and explicit acceptance/error acknowledgments. Do not coalesce actions like display frames or blindly retry unacknowledged mutations. Prevent duplicate/stale actions and stale-session confirmations from committing. Exceeding bounded input capacity must produce an explicit failure/cancel path, not silent loss or later replay. Frame coalescing remains allowed. Version parent/child protocol together and fail safely on mismatches. Preserve heartbeat progress, startup/stall deadlines, owned-child cleanup, descriptor isolation, and close intent even under action floods/backpressure. A close request cannot become trapped behind an unbounded action backlog. Once shutdown intent is accepted, discard remaining local mutation events and do not commit another draft; preserve the normal application checkpoint/error decision rather than reporting a successful shutdown unconditionally.
