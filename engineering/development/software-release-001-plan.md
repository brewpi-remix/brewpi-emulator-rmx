# 0.0.1 final software release plan

Date: November 16, 2026. Status: reviewed and corrected; the owner authorized committing and pushing this plan, assessment, and navigation links to main, with no final-version implementation or qualification started. Planning baseline: main at 9d3ec2177ab761e5b289ff67a39d03becf2d63d7. Original planning prose is copyright 2026 Lee Bussy under the root [MIT License](../../LICENSE.md). This documentation publication supersedes the earlier review-only stop before committing or pushing. It does not approve the proposed R3 reuse route or authorize implementation. Later construction, testing, final-candidate source publication, tagging, and release publication require their own authorization.

## Scope and authoritative baseline

Deliver a distinct, accepted 0.0.1 software build for native Linux amd64 and ARM64, retaining the selected Debian 12 runtime/toolchain scope and development-platform checks in the [release policy](software-release-policy.md). Preserve the [behavioral contract](../protocol/behavioral-contract.md), [firmware findings](../protocol/firmware-findings.md), original fixtures, and independently authored MIT implementation. Follow selected Arduino action/reaction, including deterministic bugs; retain the expressly approved [local-control behavior](rotary-controls-plan.md). New ambiguities require documented behavioral findings, not invented responses or unsolicited firmware corrections.

Physical Pi qualification, systemd activation, and Arduino characterization are excluded from every stage, acceptance gate, and completion claim in this plan. Inert unit-file syntax and isolated command-lifecycle checks remain software checks; they authorize no service activation. The nine characterization cases remain unresolved and must not become passing fixtures or final-release conformance claims. No deployment, reference-repository modification, GPIO/serial-controller operation, branch-rule activation, signing-key provisioning, or new paid service is included.

The published [0.0.1-rc.1 prerelease](https://github.com/brewpi-remix/brewpi-emulator-rmx/releases/tag/0.0.1-rc.1) targets f717d36364778ad48cd28bb5ae5a221c29c5db49. The local publication receipt at runs/rc1-publication-20261116/publication-verification.json records verification of all 18 public downloads, the unchanged five qualified archives, unsigned annotated tag object 4018e37fd4d2cfecf2f38ce2f62e91ca46575385, and explicit acceptance of the narrow R6 CI exception. This plan uses that saved publication evidence; it performs no new remote publication check. Preserve that release, tag, archives, receipts, historical source snapshots, and accepted evidence unchanged.

There is no identified mandatory new feature or minimum RC waiting period. Triage actual RC feedback and open defects before selecting final inputs. A final application version, new archives, exact source association, current acceptance, and final publication approval are still required. Renaming RC archives or changing the GitHub prerelease flag would leave rc.1 executable metadata and cannot produce 0.0.1.

### Recommendation and decision gate

Recommend conditional reuse of the completed original endurance/resource observations for a final candidate whose only application delta from the published RC is final-version metadata. Combine them with the accepted controls assessment and fresh exact-final-package checks below. This avoids repeating successful 24-hour and six-hour workloads merely because version metadata changes an executable hash. Describe the resulting acceptance as historical endurance evidence plus final-candidate impact assessment and focused validation; never describe final executable bytes as having completed those historical soaks.

This is a proposed, unapproved reuse route. The [existing policy](software-release-policy.md#contribution-repository-rules-and-publication-sequence) normally requires fresh R3 evidence for a new executable/helper/runtime identity. The controls exception and R6 CI exception do not automatically extend to final 0.0.1. Before using the recommendation, obtain explicit owner acceptance of a narrowly recorded final-version reuse decision/policy amendment after reviewing the actual final delta and retained evidence. If reuse is not approved, the ordinary full R3 gate remains required. Saving this plan does not amend that policy or authorize execution.

Keep original threshold definitions and report failed attempts and verified cleanup.

Run local regression and provenance checks, then obtain all nine executed hosted contexts for the exact final candidate source/attempt as required by policy. Use the [R5 actual-artifact audit](../licenses/software-release-r5.md) as the baseline, then inspect final linker maps, ELF dependencies, startup/archive members, used headers, compiler eligibility, and installed files. Original project work remains MIT; GNU compiler/runtime/startup material retains its separate terms. Do not label the entire executable solely MIT. Reuse unchanged inner GNU source bytes only after hash/version verification, with final-package association and complete license/build material. Regenerate final-version notices/source companions and checksums as needed; do not treat renamed RC archives as final qualification.

Acceptance: independently authored original work, accurate complete distribution notices, source/build obligations satisfied for inspected final artifacts, no unexplained dependency, and all required companions included. Save release notes and an operating handoff describing installation, version/protocol identity, controls, persistence, supported platforms, troubleshooting, unsigned/signed status, known limits, and exclusions. Perform an adversarial source/evidence/artifact assessment, fix authorized issues, rebuild/revalidate affected inputs, and repeat assessment until no unresolved release-blocking issue remains. Retain explicit nonblocking limitations. Stop for owner review with a concrete acceptance checklist and publication manifest. Saving or reviewing that dossier does not tag or publish.
