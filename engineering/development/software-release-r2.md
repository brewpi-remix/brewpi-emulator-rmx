## Execution contract

The original [regression workflow](../../.github/workflows/regression.yml) owns exactly the nine PR/main names frozen in the [R1 policy](software-release-policy.md). It runs on pull requests and main pushes without path filtering, schedules, trusted-target execution, or release permissions. All jobs use contents-read permissions, 60-minute timeouts, credential-free checkout, and verified immutable action revisions. References are provisioned separately at the six [recorded commits](../../tests/ci/references.json); no implementation enters the emulator tree. The completion job uses always(), requires success from each dependency, and rejects missing, stale, nonexecuted, mismatched producer/run/attempt/workflow/source receipts or omitted native/helper proofs. Candidate validation additionally refuses a PR synthetic merge in place of its exact frozen commit. These are execution receipts, not signed attestations or a substitute for owner review of untrusted changes.

Linux hosts use native ubuntu-24.04/ubuntu-24.04-arm runners, with offline Debian 12 GCC 12 guests. The host and guest architecture must agree; QEMU cannot satisfy a native lane. macos-15 ARM64 is development-only. Both Linux configurations run all six named CTest suites, and the macOS lane runs Debug, ASan/UBSan, and applicable stdlib helper checks. Linux Release lanes also provision hashed official CMake 3.16.9 and Python 3.9.25 sources and exercise all native suites on a copied original source tree without Git or reference checkouts, using the provisioned tools and disabled container networking. The core executable acquires no Python dependency.

The new native runner invokes CTest from its build directory, avoiding the newer --test-dir option. CMake and Python helper preflights reject disabled assertions. Existing helper regressions retain their checks for interrupted/failed children, incomplete evidence, source/reference mutations, foreign ownership, and failed/unverifiable cleanup. New original negative tests cover completion receipt identity, omitted checks, failed builds, assertion optimization, frozen versions/commits, changed/missing/extra/symlinked payload files, wrong ELF architecture, and absent package inputs.

## Explicit payload modes

Existing launchers default to source-build. Packaged-input requires an extracted prefix tree, a separate frozen manifest, and an exact candidate source commit expectation. The manifest names schema 1, candidate version 0.0.1-rc.1, source commit, architecture, install prefix, full application version output, and SHA256 hashes for exactly the six installed original files. ELF class/endianness/machine, every file, and application version are checked before process workflows. Missing or incorrect inputs fail rather than selecting a build-tree executable.

Integration still builds its independent native driver and runs all six source suites; those results are explicitly separate from the chosen executable used for all 17 real host/panel workflows. Qualification similarly retains both source-native configurations and the shared-library-option build, then uses the selected payload for installed readiness, runtime, service command, library/ELF inspection, and operating-file inventory checks. It requires unit commands to select the installed executable and helper. This is not a clean-runtime candidate acceptance: the qualification container intentionally contains a toolchain, and R4 must separately inspect final archive bytes, runtime ABI/symbol/ISA requirements, and a toolchain-free runtime.

Payload hashes are recorded before and after execution, at integration restarts, around service commands, and for runtime process starts. Source fingerprints continue to audit original source inputs, including CI and governing docs; they are not proof of an executable's build provenance. Installed source-build bytes are also checked for substitution. All nine runtime records and 17 workflow names must be present exactly, rather than accepting duplicate anonymous passing rows.

R2's [package fixture helper](../../tests/ci/package_fixture.py) stages a controlled mode-test input with an explicit fixture-only purpose. Its executable still reports 0.1.0 (development), with that exact expectation in the fixture manifest. It does not freeze, build, or qualify the actual 0.0.1-rc.1 release. R4 owns the later application-version and artifact work. Firmware identity remains 0.2.13/8f1fa12 with the existing personality fields.

## Reproduction and evidence

Use a new output directory for each attempt. Existing evidence is never overwritten or accepted for another run. Native checks are available through python3 tests/ci/native.py NEW_BUILD release (or debug/sanitize); helper regressions use the existing integration/checks.py, qualification/launcher_checks.py, qualification/checks.py, and new ci/checks.py entry points. Run the specification checker with the six prepared sibling references. The [CI entry-point guide](../../tests/ci/README.md) gives exact isolated and package-mode commands.

Only original receipt JSON is uploaded by CI, with seven-day retention. Raw host/panel streams, screenshots, package notices, environment inventories, and detailed failure logs stay in ignored local/disposable evidence by default. No release payload is uploaded. Before later candidate acceptance, preserve required reports in the owner-controlled durable evidence store and review their provenance and privacy. Current read-only GitHub inspection confirms Actions enabled with all actions allowed; runner allocation and every hosted architecture result remain unverified until actual publication and execution.
