## Purpose, baseline, and boundaries

Complete the remaining software validation and release engineering for a deliberately scoped Linux release. The five original milestones and [cross-milestone review](cross-milestone-review.md) are complete and published; this plan does not reopen them as unfinished features. Existing evidence includes six native suites, all 48 source-defined reviewed cases, 17 real pinned host/panel workflows, 25 focused helper regressions, Linux ARM64 Release/sanitizer/install/runtime checks, and development checks on macOS. Earlier Linux x86-64 tests used emulation/direct compiler builds and are not a current native release-build qualification. There is no active CI, release package, or published software release.

The [project contract](../../CONTRACT.md), [implementation plan](../../IMPLEMENTATION_PLAN.md), [behavioral contract](../protocol/behavioral-contract.md), [firmware findings](../protocol/firmware-findings.md), and [provenance gate](../licenses/README.md#review-gate) remain governing requirements. Follow Arduino action/reaction, including deterministic bugs, while independently authoring all changes. Never change wire identity, numeric semantics, partial stores, timing thresholds, discovery quirks, diagnostics, LCD bytes, or host-profile wall clocks merely to simplify packaging, improve a benchmark, or clear a test failure. The application's release version remains separate from serial n's firmware identity.

| In this plan | Explicitly excluded |
| --- | --- |
| Software support policy, CI, regression gates, sustained-operation/resource checks, generic Linux build qualification, source/binary artifact preparation, versioning, reproducibility, distribution inventory, and release-candidate handoff. | Physical Raspberry Pi execution, Pi OS/model/SD-card/power qualification, physical-controller access, firmware flashing, GPIO/USB/Bluetooth hardware, systemd activation/enablement/boot/namespace qualification, and new host service/dependency/reconnect automation. |
| Document existing compatibility limits prominently in candidate metadata and release notes. | Characterizing or claiming success for the nine Arduino cases, additional undefined shift/overflow outcomes, bus transactions, nested physical diagnostics, or complex electrical histories. No Arduino build or reference-firmware execution belongs in these work packages. |
| Build and inspect the existing original service example as inert package content. | Installing it into a live unit directory, starting a systemd manager, enabling a unit, modifying a live BrewPi installation, or presenting syntax/command checks as activation evidence. |

A candidate may be ready within these software limits while the excluded gates remain open. No work package intentionally exercises or depends on resolving them. An ordinary advertised workload that encounters a fidelity guard or unexpected failure still fails its acceptance gate; an exclusion cannot convert that failure into a pass. Hold the affected artifact until a source-defined original fix or an explicitly reviewed support-scope change is possible within the exclusions. If software validation uncovers a discrepancy requiring excluded Arduino evidence, record the limitation and stop the affected compatibility claim; do not invent an exact result or silently expand this plan. A newly found source-defined discrepancy requires an independently written behavioral fact/regression and an original fix preserving the firmware reaction.

### R3 — Qualify sustained operation and software recovery

Author an original opt-in sustained-test harness, separate from normal PR tests. Use isolated generic Linux targets with pinned inputs, unprivileged instances, private state, capped/rotated harness captures, and a fresh evidence directory. Measure emulator resources separately from the external host/browser/harness. Only one client reads a PTY: use the real host's socket/cache while the host owns serial, or use a sole original native client in a separate phase. Never add a second serial consumer that steals protocol bytes.

The current 900-second container launchers and short per-process qualification timeouts are not soak supervisors. Provide a separate bounded long-run supervisor, heartbeat/progress records, interruption handling, and final cleanup/evidence validation. Verify the chosen provider's runtime limits before scheduling: if a CI job cannot accommodate 24 continuous hours, use a separately authorized disposable generic Linux environment for the trusted frozen candidate and collect its results through the candidate gate. Splitting observation across fresh emulator processes or separate short jobs does not satisfy a continuous soak. No physical Pi or systemd manager is required.

Run these minimum workloads for each advertised Linux binary architecture using the frozen R4 Release executable/helper hashes and actual runtime package set. The two long soaks are continuous runs of one emulator process each; keep lifecycle stress separate so repeated restarts cannot hide memory growth. Do not shorten a soak by counting simulated hours as wall hours:

| Workload | Proposed observation and acceptance |
| --- | --- |
| 24 wall hours at 1x | Seven assigned devices, ordinary host polling and wall-clock profile disabled/resumed segments, heating/cooling demands, and controlled readbacks. Require expected controller/store effects, no unexpected exit, no unexpected framing or lost/reordered required bytes relative to the behavioral contract, no failed assertions, and verified cleanup. Record all stalls and their declared firmware blocking context. |
| Six wall hours at 60x | Constant-target/scenario phases with fixed seed, optional noise/lag/fermentation, and declared wall-clock workloads. Cover repeated 16-bit-second wraps without correcting firmware wrap bugs. Require achieved pacing within the existing +/-15% window on the declared host and no dropped replies under controlled backpressure. Host profile/log/chart time remains wall time. |
| Lifecycle stress | At least 100 controlled stop/restart or checkpoint/resume cycles, including live-versus-saved differences and complete engine snapshot comparisons at quiescent paused boundaries. Include client reopening and deliberate SIGKILL/stale-link recovery using the documented owned-link procedure. No automatic checkpoint fallback or new stale-path replacement policy. |
| Host-environment faults | Exercise corrupt/mismatched input, scenario/output aliases, storage failure before replacement, and failure during evidence collection/cleanup. Where a filesystem error occurs after rename, require an explicit failure and inspect the resulting file; do not promise old-byte retention, invent rollback, or claim power-loss durability. No physical power interruption is part of this work. |
| Clock boundaries | Extend original deterministic driver tests near the 16-bit seconds and 32-bit millis boundaries. Clearly label constructed time/history; do not wait for hardware, claim physical execution, or derive expected output from the emulator under test. |

R1-frozen Release-only resource gates: emulator peak RSS no more than 128 MiB, last steady-hour median RSS no more than 8 MiB above the first steady-hour median, and no increase in quiescent FD/thread counts across lifecycle cycles. Obtain the complete process-lifetime RSS peak from documented OS high-water accounting and collect same-PID RSS trends at intervals no greater than one second; sampled maxima alone do not prove the peak. Preserve units and measurement method. An unexplained observation/heartbeat gap exceeding five seconds makes a continuous run incomplete; do not interpolate or count suspended/stopped time. Use monotonic duration with UTC audit times, and retain peak and trend evidence rather than just endpoint values. Define the first 30 minutes as warm-up; compare the first complete steady hour after warm-up with the final complete hour of each continuous run. Record the measurement method and actual runtime binary hash. FD/thread comparisons use matched quiescent phases of the emulator and its owned process set, not global host counts or resources of an unrelated client. Use a short diagnostic pilot before the full acceptance run; it does not change the R1-approved budgets automatically. Any budget revision must be documented before rerunning acceptance, with the failed attempt retained; do not silently move thresholds to accept a leak. Sanitizer runs and external clients have separate overhead and do not share the Release RSS limit.

Bound evidence storage by validating the serial stream online, retaining sequence/error counters and incremental digests, and rotating only already validated harness records with sufficient original summaries to audit the result. Never discard transport bytes to meet a capture budget or treat a truncated/incomplete report as passing. If capture/storage fails, preserve the failure and require cleanup. Protocol matching must retain deliberate non-UTF-8 LCD bytes and unescaped diagnostic behavior; it must not impose strict local-JSON rules on firmware serial data.

Sample ordinary n query latency in a sole-client phase against the existing less-than-one-second test bound, and preserve the existing 0.6–2.5 wall-second incomplete-token window. These bounds cover the declared software workload only; unresolved bus/conversion/artifact paths have no blanket latency promise. Report CPU usage, disk/capture growth, achievable acceleration, and host contention even where no universal CPU limit is asserted.

Acceptance: all workload/resource/recovery gates pass with duration, architecture, seeds, exact binaries, counters, timing, resource samples, and cleanup recorded. Investigate anomalies and add original regressions/fixes as needed. Close each defect or explicitly hold the affected release claim; plausible thermal graphs alone are insufficient.
