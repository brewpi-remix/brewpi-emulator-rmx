## Governing behavior, provenance, and scope

Arduino behavior, including deterministic bugs, remains authoritative under the [contract](../../CONTRACT.md), [behavioral specification](../protocol/behavioral-contract.md), and [findings](../protocol/firmware-findings.md). No release/platform/test convenience may replace its parser, mutation order, defaults, timer thresholds, diagnostics, LCD bytes, or persistence effects with cleaner behavior. Host profiles and serial-token deadlines remain wall time at every simulation rate.

All new implementation, tests, tooling, generated project metadata, and prose must be independently authored under MIT with retained notices and SPDX identifiers where supported. Copying, translating, adapting, or mechanically rewriting BrewPi/Fuscus routines, headers, tests, generated tables, or assets remains prohibited. Existing original MIT project helpers may be reused with their notices. External clients, tools, and system libraries retain their own terms and require the actual [provenance review](../licenses/README.md#review-gate); no formal clean-room claim is made.

The first software release supports the existing single chamber1 personality and pinned host/panel pair. No new hardware identities, panels, modes, or automatic host reconnect behavior are added. Pi qualification, systemd activation/enablement/boot/sandbox qualification, Arduino characterization, reference-firmware execution, physical-device access, GPIO/USB/Bluetooth/flashing, physical power-loss durability, and live deployment are excluded. The nine characterization cases and additional undefined/artifact-dependent outcomes remain disclosed limitations with no passing oracle. A normal advertised workload that encounters a guard or unexpected failure holds the affected candidate; exclusions do not turn that failure into a pass.

## Artifact, prefix, and trust policy

The first candidate has exactly one architecture-independent original source tar.gz archive and two Linux binary tar.gz archives, plus original checksum/build/dependency/license manifests and release notes as sidecars. Future names are brewpi-emulator-rmx-0.0.1-rc.1-source.tar.gz, brewpi-emulator-rmx-0.0.1-rc.1-linux-amd64.tar.gz, and brewpi-emulator-rmx-0.0.1-rc.1-linux-arm64.tar.gz. Publish none in R1. Use SHA-256 with unambiguous filenames; manifests do not hash themselves or mutate a frozen source commit. Canonical archive/checksum manifests contain deterministic payload/input data. Live validation receipts, host IDs, wall-clock run times, and resource samples stay separate; these audit records need not reproduce byte-for-byte and cannot be inserted later into accepted archives.

Configure the candidate prefix as /usr/local. Binary archives contain the existing prefix-relative bin/libexec/share tree beneath one named top-level archive directory; staging/extraction instructions must distinguish that directory from the install prefix. The payload begins with the six original installed project files: executable, readiness helper, inert service example, MIT license, third-party notices, and standalone runbook. R5 may require additional notice files; declare and review any expansion before accepting the resulting new archive hashes. The service example keeps configured absolute paths and is not a relocatable or activated installation. Foreground execution uses explicit private serial/state paths; configured-prefix command checks occur only inside disposable test environments.

Source archives contain the reviewed original build/source/tests/fixtures/configuration/documentation required for source builds and offline native tests after prerequisites are installed. They require no Git checkout, reference source, or network fetch for those builds/tests. Pinned-source static checks and actual host/panel workflows remain separate checks needing the prepared external references. Do not include .git, credentials, ignored state/captures/builds, local agent/editor data, tool images, downloaded dependencies, reference application source/assets, or raw external evidence. Reject unsafe archive paths/links, unexpected entries, and privileged file modes.

The first RC is an unsigned software candidate with SHA-256 integrity manifests and an exact reviewed source commit. No signing key, OIDC attestation setup, or signature claim is introduced. Checksums do not prove authenticity; any later authorized public RC is obtained from the project's GitHub release channel and explicitly labeled unsigned. Signing/attestation can be selected later through a separate policy revision before the corresponding publication; it is not silently implied by GitHub hosting or a commit hash. R6 must present this unsigned status with the actual artifact audit for owner publication review.

Original project work remains MIT. No archive or compiled binary receives a blanket MIT declaration for external material. R5 inventories actual original, incorporated/bundled, and required external components, including applicable compiler/runtime terms, and includes required notices. No reference implementation reuse is permitted even where another license might allow it. A failed provenance gate holds the artifact; no root-license replacement or quiet copyleft incorporation resolves that gate.

## Sustained-operation environment and frozen budgets

Keep R3's 24 wall hours at 1x, six wall hours at 60x, at least 100 separate lifecycle cycles, host-environment faults, and original clock-boundary tests for each advertised Linux architecture. The continuous soaks use one emulator process each; restart cycles cannot substitute for a memory-growth observation. Workloads, seeds, target/profile histories, and expected source-defined reactions must be fixed in an original scenario/test manifest before the full runs. These tests exercise the existing personality, not excluded Arduino/bus cases.

GitHub's documented hosted-job limit is six hours. Therefore the 24-hour soak and the full six-hour soak plus setup/cleanup cannot be accepted as ordinary hosted jobs. Assign a trusted generic Linux environment for each native architecture, with a supervisor outside the short CI job lifetime, or an explicitly authorized dedicated trusted runner. CI may later verify and summarize those preserved reports without keeping a hosted poll job alive for a day. R1 chooses owner-provided environments as the default; no cloud rental, billing change, persistent untrusted-PR runner, or runner registration is authorized. Source: [GitHub Actions limits](https://docs.github.com/en/actions/reference/limits).

Reserve at least 36 uninterrupted wall hours per architecture to allow the two continuous runs plus setup and recovery work, extending the reservation if the documented lifecycle tests need more time. The environment must provide native CPU execution, a declared isolated CPU/RAM allocation, adequate disk for the locked image and bounded evidence, working unprivileged devpts, and the recorded Debian 12 runtime. Linux containers on a suitable native non-Pi host are permitted. Record actual host/VM/container architectures, CPU/RAM/disk allocation, immutable images/package versions, and load; do not claim a universal performance budget from an unspecified machine. R3 must not change the user's host sleep/power settings, reserve resources, register runners, or provision machines without the necessary later authorization.

| Gate | Frozen R1 acceptance rule |
| --- | --- |
| Emulator Release RSS | Peak no more than 128 MiB, using documented OS per-process high-water accounting across the complete lifetime, including startup and shutdown; a sampled maximum alone is insufficient. Collect same-PID RSS trend samples at intervals no greater than one second. Final steady-hour median must be no more than 8 MiB above the first complete steady-hour median following a 30-minute warm-up. Record units and collection method; do not substitute cgroup/cache-inclusive memory for RSS without a reviewed policy revision. Sanitizer/client/browser/harness resources are separate and reported. |
| FD/thread/process recovery | No growth in matched quiescent emulator/owned-process FD or thread counts across cycles; no owned process, PTY endpoint, lock ownership, or container leak after documented cleanup. Expected retained lock files/stale-link behavior are evaluated under the existing lifecycle contract, not deleted by a new automatic policy. |
| Pacing | Achieved factor within +/-15% of requested 1x/60x for the declared long workload and environment. Preserve firmware thresholds, integration step, and wall-clock profile semantics. |
| Ordinary query latency | Sole-client n sample maximum below one wall second in the declared workload; collect distributions and every outlier. No second PTY consumer while the host owns serial. |
| Incomplete token wait | Preserve the existing 0.6–2.5 wall-second validation window at the declared rates. This is no bound for excluded physical/artifact paths. |
| Evidence and protocol | Online matching of source-defined byte behavior, counters/digests and validated rotation; no dropped transport bytes, incomplete accepted result, or new strict-JSON requirement for firmware output. Preserve CP437 LCD bytes and unescaped diagnostics. |
| Resource context | Report CPU, disk/capture growth, background load, and actual acceleration. No unmeasured universal CPU percentage or Pi capacity claim. |

Measure active observation duration with a monotonic clock and retain UTC start/end times for audit. The sampler records an independent heartbeat and detects observation gaps or host/VM suspension; an unexplained sample/heartbeat gap exceeding five seconds makes the continuous resource run incomplete. Do not interpolate missing data, count stopped time, restart the process, or stitch shorter runs to reach 24/six hours. Preserve interruption/failure evidence and verified cleanup, then rerun a fresh complete workload when resources are available. Test this accounting with original negative cases in the later authorized harness work.

A short pilot is diagnostic only. If it fails these budgets, retain the failure and investigate the implementation/environment; a proposed budget or workload change needs a documented R1 revision reviewed before a fresh acceptance run. No automatic threshold relaxation, time shortening, new firmware rejection, or characterization counted as pass is allowed.

## Contribution, repository rules, and publication sequence

Use main as the release line, with reviewed PRs targeting main under the existing contribution model. No new permanent development branch is introduced. Keep direct maintainer commits/pushes subject to explicit owner instruction, consistent with earlier authorized publications. The R1 preparation snapshot reported one write-capable collaborator through a read-only query. Select the single-maintainer path: require all nine PR/main contexts (eight executed lanes plus pr-validation) and a recorded technical review with the owner's manual acceptance/merge decision, without requiring an unavailable second-account approval. An automated review is recorded as such, not represented as another human/GitHub approver. When repository protection is separately authorized, enforce the required checks and prohibit force-push/tag replacement; no automatic merge is enabled. Verify collaborator capacity and actual rules before activation. If a second eligible maintainer is added, a policy revision can require one non-author approval; do not silently change the rule or bypass failed checks.

The future local sequence is R2 CI/harness foundations, provisional R4 candidate freeze, exact-byte R3/final R4 validation and R5 audit, then R6 handoff. Every frozen candidate attempt has an immutable version/commit/input manifest and payload hashes. A corrected frozen candidate uses the next RC number; failed setup before an artifact freeze can be retried under a new attempt ID without pretending a candidate passed. A notice/payload/version/input change returns to R4 and creates new hashes and affected evidence; no in-place edit of frozen/accepted bytes is allowed. Unchanged evidence can be carried only when its complete input identity still matches and its scope is explicitly documented; a new executable/helper/runtime identity requires fresh R3 evidence. Public RC publication, if later authorized, uploads only the accepted rc.1 bytes and original sidecars to the intended repository/reviewed source commit under the new annotated tag. Before publishing, verify repository/commit/version/checksums and unsigned/prerelease status, refuse an existing conflicting tag/version, and preserve prior releases. Final 0.0.1 is a separate build/validation/publication cycle, not an RC label change.

Source commit/push, workflow publication, repository-rule activation, candidate construction, tags, GitHub Release creation, public artifact upload, and deployment are separate actions whose authorization follows the active task. R1 creates none of them. No signing/provenance claim or all-green report substitutes for the owner's later publication instruction.
